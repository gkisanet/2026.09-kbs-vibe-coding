# ✍️ 프롬프트에서 컨텍스트 엔지니어링으로

> **이 문서가 답하는 질문**: 두 용어는 정확히 무엇이 다른가? 왜 이름이 바뀌었는가?
> **핵심 메시지**: **"프롬프트 엔지니어링은 '문장'의 기술, 컨텍스트 엔지니어링은 '예산'의 기술이다."**

---

## 1. 두 용어의 관계를 그림 하나로

```
┌──────────────────────────────────────────────────────────────────────┐
│  모델이 실제로 보는 것 = "컨텍스트 창" 하나                            │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │  시스템 프롬프트          ← 프롬프트 엔지니어링의 영역           │  │
│  ├────────────────────────────────────────────────────────────────┤  │
│  │  도구(툴) 정의 목록                                             │  │
│  ├────────────────────────────────────────────────────────────────┤  │
│  │  스킬 / 참고문서 (그때그때 로드됨)                               │  │
│  ├────────────────────────────────────────────────────────────────┤  │
│  │  이전 대화 기록 (1턴 ~ N턴)                                     │  │
│  ├────────────────────────────────────────────────────────────────┤  │
│  │  도구 실행 결과들 (파일 내용, 검색 결과, 에러 로그…)             │  │
│  ├────────────────────────────────────────────────────────────────┤  │
│  │  이번 턴 사용자 입력      ← 프롬프트 엔지니어링의 영역           │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│   ⭐ 이 상자 전체를 어떻게 채울 것인가 = 컨텍스트 엔지니어링           │
│      그중 두 칸을 어떻게 쓸 것인가   = 프롬프트 엔지니어링             │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

> 🎯 **포함 관계입니다. 경쟁 관계가 아닙니다.**
> **컨텍스트 엔지니어링 ⊃ 프롬프트 엔지니어링**

---

## 2. 왜 이름이 바뀌었나 — 병목이 옮겨갔기 때문

| | 프롬프트 엔지니어링 시대 | 컨텍스트 엔지니어링 시대 |
|---|---|---|
| **시기** | 2022~2024 | 2025~ |
| **전형적 상황** | 사람이 채팅창에 한 번 입력 → 한 번 답 | 에이전트가 100턴 넘게 도구를 돌림 |
| **컨텍스트 대부분을 차지하는 것** | **사람이 쓴 글** | **도구 실행 결과** |
| **병목** | 모델이 지시를 못 알아들음 | 창이 쓰레기로 가득 참 |
| **핵심 질문** | "어떻게 써야 잘 알아들을까?" | "무엇을 넣고 무엇을 뺄까?" |
| **자원 관점** | 무제한 (짧으니까) | **한정된 예산** |

### ⭐ 결정적 변화: 창을 채우는 주체가 바뀌었다

```
[2023년 — 사람이 채움]
 컨텍스트 8,000토큰 중
   ├─ 시스템 프롬프트   500
   ├─ 사용자 질문       200
   └─ 남는 공간       7,300      ← 여유롭다

[2026년 — 도구가 채움]
 컨텍스트 200,000토큰 중
   ├─ 시스템 프롬프트    2,000
   ├─ 도구 정의          3,000
   ├─ 사용자 질문          200
   ├─ ⚠️ 파일 읽기 결과  80,000   ← 이게 문제
   ├─ ⚠️ 검색 결과      40,000
   ├─ ⚠️ 에러 로그      30,000
   └─ 남는 공간         44,800
```

> 🔗 배포 교재 **[3-0. CONTEXT_관리.md](../교육자료%20배포/3-0.%20CONTEXT_관리.md)** 3.3절
> "바이브 코딩에서 Context를 가장 많이 먹는 것 — **대화가 아니라 도구 결과**"
> 가 정확히 이 이야기입니다. 이미 교재에 들어가 있습니다.

## 3. 컨텍스트 엔지니어링의 4가지 전략 (영상 정리)

> 🎬 "개별 세션에서 **필요한 것을 필요한 시간에 담자**"

### 전략 ① — 밖에 써놓고 나중에 꺼내오기 (메모리)

```
[문제] 세션이 끝나면 다 잊어버린다. 다음에 또 처음부터 설명해야 한다.

[해법]
  세션 중:  중요한 걸 알게 되면 → 파일에 적어 둔다
             (예: /memories/project-conventions.md)
  다음 세션: 그 파일을 읽고 시작한다

[비유] 신입에게 매번 다시 설명하는 대신, 업무 인수인계 노트를 쓰게 하는 것
```

⚠️ **주의**: 이건 "학습"이 아닙니다. 모델 가중치는 그대로입니다.
**시스템이 참고할 외부 메모를 만드는 것**입니다. (→ 1번 문서 A-11)

---

### 전략 ② — 필요한 것만 불러오기 (스킬 / 툴 검색)

**핵심 원리: 점진적 공개(progressive disclosure)**

```
                  나쁜 방식                     좋은 방식
                  ─────────                    ─────────
시스템 프롬프트     매뉴얼 전문 50페이지          "매뉴얼 목차"만 1페이지
                  (매 요청마다 전송)                  ↓
                        ↓                     필요한 장(章)만 그때 읽음
                  · 매번 돈 나감
                  · 대부분 안 씀
                  · 신호가 묻힘
```

**같은 원리를 쓰는 것들** — 이걸 알면 여러 용어가 하나로 정리됩니다:

| 이름 | 무엇을 계층화하나 |
|------|-----------------|
| **스킬 (Skills)** | 작업 노하우 매뉴얼 |
| **AGENTS.md 계층화** | 프로젝트 규칙 문서 |
| **툴 검색 (tool search)** | 도구 정의 (도구가 100개면 전부 안 싣고 검색해서 씀) |
| **RAG** | 지식 문서 |

> 🎯 **강사용 한 줄**: **"전부 미리 주지 말고, 어디를 보면 되는지만 알려줘라."**
> 이 한 문장이 스킬·AGENTS.md·RAG·툴검색을 전부 설명합니다.

---

### 전략 ③ — 짧게 줄여 보관하기 (요약 / 삭제)

```
┌────────────────────────────────────────────────────────────┐
│  두 가지 방식이 있고, 성격이 정반대입니다                    │
├────────────────────────────────────────────────────────────┤
│                                                            │
│  A) 요약(compaction) — "줄여서 남긴다"                      │
│     1~80턴 원문 ───요약───▶ "지금까지 이런 일이 있었음"      │
│     ✅ 흐름이 유지됨                                        │
│     ⚠️ 디테일이 소실됨 ("아까 그 파일명 뭐였지?" 불가)       │
│                                                            │
│  B) 삭제(context editing) — "그냥 버린다"                   │
│     100턴 전 파일 읽기 결과 ───삭제───▶ (없음)              │
│     ✅ 지금 필요 없는 건 확실히 사라짐                       │
│     ⚠️ 나중에 필요하면 다시 읽어야 함                       │
│                                                            │
│  → 영상에서 "만수(Manus) 같은 사람들이 좋아하는              │
│     옛날 툴 실행 결과 다 없애버리는 거"가 B입니다            │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

---

### 전략 ④ — 아예 쪼개기 (서브에이전트)

```
[문제] 하나의 창에 다 넣으면 어차피 넘친다.

[해법] 창을 여러 개 만든다.

   메인 에이전트 (창 A)
     │  "이 20개 파일을 조사해서 요약해 와"
     ├──▶ 서브에이전트 1 (창 B: 파일 1~7 읽음, 8만 토큰 소모)
     │       └─ 결과 요약 300토큰만 반환  ← ⭐ 메인 창에는 이것만 들어감
     ├──▶ 서브에이전트 2 (창 C: 파일 8~14)
     │       └─ 결과 요약 300토큰
     └──▶ 서브에이전트 3 (창 D: 파일 15~20)
             └─ 결과 요약 300토큰

  메인 창 소모: 900토큰 (24만 토큰어치 작업을 했는데도)
```

> 💡 **이게 "울트라 모드"가 하는 일**입니다. (→ 1번 문서 D-3)
> 그리고 **토큰을 어마어마하게 쓰는 이유**이기도 합니다.
> 메인 창은 아꼈지만, **전체 소모량은 서브 3개 합쳐서 훨씬 큽니다.**

## 4. ⚠️ 게스트의 비판을 정면으로 다뤄야 합니다

> 🎬 "저는 여기 있는 것들 다… 제가 느끼기에는 **부정적인 의견**일 것 같은데,
> 진짜 일을 더 잘, **LLM이 더 똑똑해지는 방향이라기보다는 쓰는 사람이 편해지는 것 같거든요.**
> 그러니까 스킬도 굳이 따지면 근본적으로는 **그냥 프롬프트 덩어리잖아요.**"

이 비판은 **정확합니다.** 그리고 강사가 이걸 이해하고 있어야 수강생 질문에 답할 수 있습니다.

```
┌─────────────────────────────────────────────────────────────────┐
│  컨텍스트 엔지니어링이 하는 일 / 안 하는 일                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ❌ 모델을 똑똑하게 만들지 않는다                                │
│     스킬을 붙인다고 모델의 추론력이 올라가지 않음                 │
│     (가중치는 1바이트도 안 바뀜)                                 │
│                                                                 │
│  ✅ 모델이 이미 가진 능력을 낭비하지 않게 한다                    │
│     · 창이 안 차게 → 성능 저하 방지                              │
│     · 관련 정보가 묻히지 않게 → 신호 대 잡음비 개선               │
│     · 매번 같은 설명을 반복하지 않게 → 비용 절감                  │
│                                                                 │
│  ⭐ 즉, 성능을 "올리는" 기술이 아니라 "지키는" 기술이다           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 그런데 왜 그게 중요한가

| 비유 | 설명 |
|------|------|
| **엔진 vs 연비** | 스킬은 엔진 출력을 안 올린다. 하지만 연비를 두 배로 만든다 |
| **직원 vs 매뉴얼** | 매뉴얼이 직원 IQ를 올리진 않는다. 하지만 같은 실수를 반복 안 하게 한다 |
| **컴퓨터 vs 정리** | 정리한다고 CPU가 빨라지지 않는다. 하지만 파일을 못 찾아 헤매지 않는다 |

> 🎯 **강사용 답변 템플릿**
> "스킬이 AI를 똑똑하게 만드는 건 아닙니다. **AI가 멍청해지지 않게 막아주는 것**입니다.
> 그런데 실무에서 문제가 되는 건 대부분 '멍청해서'가 아니라
> '**아까 말한 걸 잊어서**' 또는 '**우리 규칙을 몰라서**'입니다. 그래서 효과가 큽니다."

## 5. 그리고 스킬의 진짜 난제 — 평가

> 🎬 "그래서 **스킬은 평가가 되게 중요하다**, 이런 의견들이 좀 많이 보이는 것 같아요"
> "근데 이거를 평가하는 게 **되게 어렵다**는 거죠"
> "A/B 테스트처럼 스킬을 쓰고 안 쓰고를 비교해야 되는데,
> 그런 거 하려면 또 **평가 데이터가 필요하고 환경이 필요하니까**"

```
┌────────────────────────────────────────────────────────────────┐
│  "이 스킬이 도움이 됐는가?"를 확인하려면                         │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│   같은 작업 100건을                                             │
│     ┌─ 스킬 켜고 실행 → 결과 A                                  │
│     └─ 스킬 끄고 실행 → 결과 B                                  │
│                    ↓                                           │
│              A와 B를 채점                                       │
│                    ↓                                           │
│   ⚠️ 그런데 "채점"을 누가 하나?                                 │
│      · 사람이? → 100건 × 2 = 200건을 사람이 봐야 함             │
│      · AI가?  → 그 AI는 믿을 수 있나?                          │
│      · 테스트가? → 코딩이면 가능. 그 외에는?                     │
│                                                                │
│   ⭐ 그래서 대부분의 팀은 "느낌상 좋은 것 같다"로 운영 중         │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

> 🎯 **여기서도 결국 "검증"이 병목입니다.**
> 이 문서 전체, 이 폴더 전체를 관통하는 주제입니다.
> **AI 시스템 설계의 난이도 = 채점의 난이도**

## 6. ⭐ 방송국 업무로의 번역

강사가 수강생에게 이 개념을 전달할 때 쓸 수 있는 매핑입니다.

| 컨텍스트 엔지니어링 개념 | 방송 현업 대응물 |
|---|---|
| 시스템 프롬프트 | 부서 업무 지침 |
| 스킬 | 업무별 표준 작업 절차서(SOP) |
| 메모리 | 인수인계 노트 |
| 오토 컴팩트 | 회의록 요약본 |
| 오래된 툴 결과 삭제 | 지난 방송 큐시트 폐기 |
| 서브에이전트 | 파트별 담당자에게 위임 후 요약 보고만 받기 |
| AGENTS.md 계층화 | 두꺼운 사규집 대신 "이 경우엔 몇 장을 보라"는 색인 |
| 검증(CI) | 송출 전 기술 점검 / 심의 |

> 💡 이 표는 **8번 문서(강사용 전달 설계)** 에서 그대로 재사용합니다.
