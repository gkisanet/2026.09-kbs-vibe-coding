### #9 — 이미 추적(Tracked) 중인 폴더의 로컬 파일 보존 및 Git 언트래킹 기법 (`git rm --cached`) (2026-08-16)

- **증상**: 개인 학습용으로 정리한 폴더(`1.교육자료/심화_AI엔지니어링/`)가 이미 Git에 커밋되어 원격 저장소에 노출된 상태에서, 로컬 디스크의 원본 파일은 그대로 두고 GitHub 원격 저장소에서만 깔끔하게 제외하고자 함.
- **원인**: Git은 이미 한번 `git add` 및 커밋된 파일에 대해 `.gitignore`에 등록하더라도 무시하지 않고 계속 추적(Track)함.
- **해결책**:
  1. `git rm -r --cached "1.교육자료/심화_AI엔지니어링"` 명령어를 실행하여 **로컬 디스크 파일은 건드리지 않고 Git 인덱스(추적 목록)에서만 삭제**.
  2. `.gitignore`에 `1.교육자료/심화_AI엔지니어링/`을 등록하여 향후 변경 사항이 다시 Git에 감지되지 않도록 차단.
  3. 커밋 후 `git push origin main`으로 원격 저장소 동기화.
- **배운 점**:
  - **`git rm` vs `git rm --cached`**: 일반 `git rm`은 하드디스크의 파일까지 물리적으로 지우지만, `--cached` 플래그를 붙이면 "Git 작업 목록에서만 제외"하므로 개인용 파일 보존에 매우 유용하다.

### #8 — 오픈소스/수업용 리포지토리 배포 시 Secrets 격리와 PII 비식별화 (2026-08-16)

- **증상**: 사내 실무용으로 개발된 크롬 확장 프로그램을 별도 공개 리포지토리로 분리하여 바이브 코딩 수업 교재로 활용하려 할 때, 코드 내에 Google Cloud RSA Private Key, API Key, 사내 시스템 계정, 임직원 실명/사번이 하드코딩되어 있어 보안 및 개인정보 유출 위험 발생.
- **원인**: 초기 개발 단계에서 빠른 프로토타이핑을 위해 인증 자격 증명과 도메인 데이터를 모듈 내부에 인라인 상수로 선언해 둠.
- **해결책**:
  1. `config.js` / `config.example.js` 설정 분리 패턴을 도입하여 자격 증명을 외부 환경 설정 객체로 일원화.
  2. `.gitignore`에 `config.js`를 등록하여 실제 운영 키가 Git 히스토리에 포함되지 않도록 차단.
  3. 소스코드 및 실습 교재 내 임직원 실명/사번을 가명 샘플 데이터(홍길동, 김철수 등)로 교체하고, "본인 부서 정보로 교체하는 실습 과제"로 유도.
  4. `README.md`에 키 주입 방법 2종(사내망 별도 파일 전달 vs 템플릿 복사)을 상세히 기술.
- **배운 점**:
  - **Secret Management의 핵심 원칙**: "코드는 공개될 수 있어도 자격 증명은 절대 커밋되지 않아야 한다(12-Factor App)."
  - **교육적 설계 (Pedagogical Design)**: 하드코딩된 내부 데이터를 가명화하면서 이를 단순 제거하는 것이 아니라, 수강생이 직접 수정해보는 실습 포인트로 전환함으로써 교육적 효과를 극대화할 수 있다.

### #7 — 프로젝트 거버넌스 문서와 도메인 교육자료의 계층 분리 (2026-08-16)

- **증상**: 프로젝트 관리 문서(WBS, 변경 이력, 인수인계, 아키텍처)와 크롬 확장 프로그램 자습용 튜토리얼 문서들이 한 `docs/` 폴더에 섞여 있어 신규 학습자가 어떤 순서로 문서를 읽어야 할지 혼란스럽고, AI 에이전트의 Context Window에도 불필요한 토큰 부하를 유발함.
- **원인**: 문서의 대상 독자(Audience)가 **"프로젝트를 유지보수/인수인계하는 개발자/AI"**와 **"확장앱 코드를 학습하려는 수강생"**으로 상이함에도 물리적 위치를 분리하지 않음.
- **해결책**:
  1. 크롬 확장앱 폴더(`3.autoreport_크롬확장앱/docs/`) 내부에 학습 순서 넘버링(`01_TUTORIAL.md` ~ `07_TROUBLESHOOTING.md`)을 적용하여 수강생 자습용 독립 패키지 완성.
  2. 루트 `docs/`는 프로젝트의 5대 핵심 엔지니어링 거버넌스 지식 베이스(`CONTEXT.md`, `TASKS.md`, `CHANGELOG.md`, `HANDOVER.md`, `LESSONS.md`)로 정예화.
- **배운 점**:
  - **문서 아키텍처 (Documentation Architecture)**: 코드베이스뿐만 아니라 문서 역시 독자와 목적에 따른 관심사 분리가 필수적이다.
  - **온보딩 마찰 최소화**: `01_`부터 시작하는 번호 매김 방식은 별도의 긴 안내 없이도 수강생의 인지 부하를 크게 낮춘다.

### #6 — 크롬 확장 프로그램의 패키지 격리와 관심사 분리(Separation of Concerns) (2026-08-16)

- **증상**: 프로젝트 루트에 크롬 확장 프로그램 소스 파일들(`manifest.json`, `contentscript.js` 등 13개 파일)과 문서(`docs/`), 3-Tier API 실습 프로젝트(`API_TEST/`), 각종 샘플 엑셀 파일이 한곳에 뒤섞여 있어 프로젝트 구조 파악과 확장 프로그램 로드/배포 시 혼선 발생.
- **원인**: 초기 단일 확장 프로그램으로 시작된 저장소에 교육 교재, 실습 샌드박스, 테스트 데이터가 점진적으로 추가되면서 루트 디렉토리의 책임이 과도하게 집중됨.
- **해결책**:
  1. `autoreport/` 전용 하위 디렉토리를 생성하여 확장 프로그램 전용 소스코드(`manifest.json`, JS 스크립트, `data/`, `_locales/`)를 일체 이관.
  2. 크롬 개발자 모드(`chrome://extensions`)에서 확장 프로그램을 로드할 때 루트 대신 `autoreport/` 폴더를 지정하도록 `README.md` 및 가이드 문서 갱신.
- **배운 점**:
  - **관심사의 분리 (Separation of Concerns)**: 프로젝트가 성장함에 따라 단일 저장소 내에서도 각 애플리케이션/모듈별로 폴더 경계를 명확히 분리해야 파일 관리, git diff 추적, 패키징 배포가 수월해진다.
  - **Chrome Extension의 독립성**: 크롬 확장은 `manifest.json`이 위치한 폴더를 루트로 인식하므로, 전용 서브폴더로 분리해도 내부 상대경로(`data/category.json`, `favicon.ico` 등) 수정 없이 즉시 독립 패키지로 동작한다.

### #5 — Socket.io 양방향 이벤트 통신과 WebSocket 룸(Room) 세션 처리 (2026-08-05)

- **증상**: 웹 애플리케이션에서 페이지 새로고침 없이 실시간으로 상대방 메시지가 도착해야 하고, 특정 방(Room)에만 메시지가 격리 전송되어야 함.
- **원인**: 단방향 HTTP 요청/응답(REST API) 모델로는 실시간 양방향 채팅을 구현하기 어려우며(폴링 방식은 서버 과부하 발생), 전체 접속자에게 브로드캐스트하면 다른 방의 대화가 섞이는 현상이 발생함.
- **해결책**:
  1. `Socket.io` 라이브러리를 도입하여 클라이언트와 서버 간의 **지속적인 TCP 연결(Full-Duplex WebSocket)** 유지.
  2. 서버 측 `socket.join(roomId)` 및 `io.to(roomId).emit(...)` 메서드를 사용하여 **특정 방 그룹 세션에만 메시지를 격리 전송**하는 룸 세션 구조 설계.
- **배운 점**: 
  - **HTTP vs WebSocket**: 단발성 CRUD 데이터 주고받기는 HTTP REST API가 유리하지만, 지속적인 양방향 이벤트 및 실시간 알림은 WebSocket/Socket.io가 필수적이다.
  - **Socket.io Room 메커니즘**: 서버 메모리에서 채널/룸 단위로 클라이언트 소켓 ID들을 관리함으로써 멀티룸 채팅 시스템을 손쉽게 구축할 수 있다.

### #4 — Context Window 용량 초과 및 RAG vs 프롬프트 주입 오해 (2026-07-30)

- **증상**: 5,000페이지 사내 매뉴얼 PDF 전체를 AI 대화창에 첨부하여 질문 시 토큰 한계 에러 발생 또는 초반 규칙 상실.
- **원인**: 대용량 문서를 통째로 프롬프트에 넣으면 Context Window 한계를 초과하거나 토큰 비용이 폭증하고, AI가 중간 내용을 무시(Lost in the Middle)하게 됨.
- **해결책**:
  1. 파일을 조각(Chunk)으로 나누어 Vector DB에 저장하고, 검색된 연관 텍스트(1~2페이지)만 AI Context에 주입하는 **RAG (Retrieval-Augmented Generation)** 시스템 도입.
  2. 대화가 길어지면 새 세션을 열고 `HANDOVER.md`를 통해 세션 상태만 복구하도록 교육 커리큘럼 구성.
- **배운 점**:
  - **"파일 업로드 ≠ 학습"**: 프롬프트 주입은 단순 오픈북 테스트일 뿐이며, 대용량 파일은 RAG 검색 방식이 속도와 비용 면에서 월등하다.

### #3 — 확장 프로그램 업데이트 시 통신 단절 (Receiving end does not exist) (2026-05-04)

- **증상**: 코드를 수정하고 확장 프로그램을 재로드한 뒤, 기존에 열려있던 ERP 탭에서 팝업의 [입력] 버튼을 누르면 콘솔에 Unchecked runtime.lastError: Could not establish connection. Receiving end does not exist. 에러가 발생하며 아무 동작도 하지 않음. 사용자는 앱을 지웠다 다시 설치해야 하는 것으로 오해함.
- **원인**: 크롬 확장 프로그램이 업데이트/재로드되면 백그라운드 스크립트와 팝업은 새로 시작되지만, 기존 탭에 주입되어 있던 Content Script는 재로드되지 않고 이전 상태로 고립(Orphaned)됨. 이때 팝업이 chrome.tabs.sendMessage로 메시지를 보내면, 고립된 구버전 Content Script는 메시지를 받을 수 있는 유효한 포트가 없어 연결 에러를 발생시킴.
- **해결책**: chrome.tabs.sendMessage의 콜백 함수 최상단에서 chrome.runtime.lastError가 존재하는지 체크하고, 에러가 발생한 경우 alert('확장 프로그램 연결이 끊어졌습니다. 페이지를 새로고침 해주세요.') 등의 명시적인 안내 메시지를 띄워 사용자가 직접 F5를 누르도록 유도함.
- **배운 점**: 
  - **크롬 확장의 생명주기(Lifecycle)**: 확장 앱의 재로드가 웹 페이지(Content Script)의 자동 재로드를 보장하지 않는다. 고립된 컨텍스트 문제를 이해하는 것은 확장 프로그램 개발의 핵심 기본기다.
  - **Graceful Degradation (우아한 실패)**: 시스템 에러(lastError)를 콘솔에만 찍고 무시하면 사용자는 고장난 것으로 착각한다. 에러를 캐치해서 원인과 해결 방법(새로고침)을 명확히 제시하는 것이 좋은 UX의 기본이다.

### #2 — 드롭다운 선택 시 부분 문자열 매칭(includes) 오탐 (2026-05-04)

- **증상**: ERP 폼에서 '송출' 키워드로 드롭다운 항목을 자동 선택할 때, 의도한 '송출'(A2000145)이 아닌 'CM SPOT 및 SCROLL 송출'(A2000130)이 선택됨
- **원인**: 옵션을 찾는 findOptionByText 함수가 includes를 사용해 부분 문자열 매칭을 하고 있었음. 옵션 텍스트가 A2000130 : CM SPOT 및 SCROLL 송출 형태로 제공되어, 내부에 '송출'이라는 단어가 포함되어 있기 때문에 첫 번째로 발견된 A2000130이 선택됨.
- **해결책**: 옵션 텍스트를 구분자(:)로 파싱하여 실제 옵션 이름 부분을 추출한 뒤, includes 대신 === 연산자를 사용해 정확히 일치(Exact Match)하는 항목을 먼저 찾도록 검색 로직의 우선순위를 변경함. 정확히 일치하는 항목이 없을 경우에만 기존의 includes 매칭을 fallback으로 수행하도록 구현.
- **배운 점**: 
  - **DOM 옵션 텍스트 매칭의 위험성**: includes나 indexOf를 활용한 부분 매칭은 예상치 못한 오탐(False Positive)을 낳기 쉽다. 데이터가 정형화된 경우 가급적 정확한 토큰을 추출해 Exact Match를 시도하는 것이 더 견고하다.
  - **Fallback 전략**: 완전히 Exact Match로만 변경하면 포맷이 살짝 다른 예외 케이스(예: 띄어쓰기)에서 매칭에 실패할 수 있다. 1차로 Exact Match를 시도하고, 실패 시 2차로 includes를 시도하는 다단계 매칭 전략이 유연성과 정확성을 모두 잡는 방법이다.

### #1 — 한셀(Hancel)로 저장된 .xlsx 파일 파싱 실패 (2026-04-07)

- **증상**: 한글과컴퓨터 한셀로 저장한 .xlsx 파일을 업로드하면, 시트 이름(SheetNames)은 정상적으로 읽히지만 실제 시트 데이터(Sheets)가 비어있어 파싱이 실패함
- **근본 원인**: 한셀은 모든 XML 태그에 `x:` 네임스페이스 접두사를 사용하며, 이것이 2가지 문제를 일으킴:
  1. **SheetJS 실패**: `[Content_Types].xml`의 ContentType 값으로 워크시트를 식별하는 내부 로직이 한셀의 비표준 구조를 처리하지 못함
  2. **XML 파싱 실패**: MS Excel은 `<row>`, `<c>`, `<v>`를 사용하지만, 한셀은 `<x:row>`, `<x:c>`, `<x:v>`를 사용하여 정규식 매칭 실패
  - 한셀의 XML 선언: `<x:worksheet xmlns:x="http://schemas.openxmlformats.org/spreadsheetml/2006/main">`
- **1차 시도 (실패)**: SheetJS의 다양한 옵션 조합으로 6가지 파싱 전략 시도 → 모두 SheetNames=7, Sheets키=0으로 동일하게 실패
- **2차 시도 (ZIP 파싱 성공, XML 셀 0개)**: ZIP을 직접 파싱하여 워크시트 XML 추출 성공. 하지만 정규식이 `<row>`, `<c>` 등 접두사 없는 태그만 매칭하여 셀 데이터 0개 추출
- **3차 시도 (완전 성공)**: 모든 정규식에 `(?:\w+:)?` 네임스페이스 접두사 패턴 추가
  1. `parseZipCentralDirectory()` — ZIP 중앙 디렉터리에서 파일 목록 획득
  2. `workbook.xml` + `workbook.xml.rels` 파싱 → 시트이름 ↔ 파일경로 매핑
  3. `DecompressionStream('deflate-raw')` API로 각 워크시트 XML 압축 해제
  4. `(?:\w+:)?` 패턴으로 `<x:row>`, `<x:c>`, `<x:v>`, `<x:si>`, `<x:t>` 등 모두 매칭
  5. 93개 공유 문자열 로드 + 127~176개 셀/시트 파싱 성공
  6. `mergeCells` 정보도 파싱하여 `!merges`에 반영
- **배운 점**: 
  - **XML 네임스페이스 접두사는 정규식에서 매우 중요하다.** `<row>`만 매칭하면 `<x:row>`는 무시된다. `(?:\w+:)?` 패턴으로 모든 접두사를 선택적으로 매칭해야 한다.
  - SheetJS 옵션을 아무리 바꿔도 content-type 기반 필터링은 우회할 수 없다. **라이브러리의 내부 한계를 이해하고, 우회 파서를 직접 구현**해야 한다.
  - `DecompressionStream`은 Chrome 80+ 내장 API로, 별도 라이브러리 없이 브라우저에서 deflate 압축 해제가 가능하다.
