# 🗺 도구 지형도 — 무엇이 무엇을 대체했는가

> **이 문서가 답하는 질문**: LangChain / LangGraph / LiteLLM / MCP / 스킬은 각각 어느 층의 도구이며, 왜 어떤 건 지고 어떤 건 뜨는가?
> **핵심 메시지**: **"층이 다른 도구를 같은 선반에 놓고 비교하니까 헷갈리는 것이다. 층부터 나눠야 한다."**

---

## 1. 먼저 층부터 나눕니다

```
┌──────────────────────────────────────────────────────────────────────┐
│  AI 애플리케이션 스택 (아래에서 위로)                                  │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  ⑥ 사용자 인터페이스     클로드 코드 / 코덱스 / 헤르메스 / 웹 채팅     │
│     ───────────────────────────────────────────────────────          │
│  ⑤ 오케스트레이션        루프 / 그래프 / 멀티에이전트 조정            │
│                          (LangGraph, 각종 에이전트 프레임워크)        │
│     ───────────────────────────────────────────────────────          │
│  ④ 컨텍스트 조립         스킬 / 메모리 / RAG / 컴팩션                 │
│     ───────────────────────────────────────────────────────          │
│  ③ 도구 연결             MCP / 함수 호출(function calling)            │
│     ───────────────────────────────────────────────────────          │
│  ② 모델 접근 추상화      ⭐ LiteLLM / OpenRouter                      │
│     ───────────────────────────────────────────────────────          │
│  ① 모델 API             Anthropic API / OpenAI API / 로컬(Ollama 등)  │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

> 🎯 **LangChain이 애매해진 이유가 이 그림에 있습니다.**
> LangChain은 ②③④⑤를 **전부 한 보따리로** 제공했습니다.
> 그런데 지금은 각 층마다 그 층만 잘하는 전문 도구가 생겼습니다.
> **보따리를 통째로 살 이유가 사라진 것입니다.**

## 2. ⭐ ②층 — "litellm도 이제 된다"의 정확한 자리

> 🎬 "그걸 쓰는 이유는 사실 **여러 개 LLM을 동시에 부를 수 있다는 것밖에 없거든요.**
> 근데 그건 사실 **LiteLLM도 되고 다 되는 거잖아요, 이제.**"

### 문제: 회사마다 API가 다르다

```
같은 "안녕이라고 말해줘"를 보내는데도…

  OpenAI:     POST /v1/chat/completions
              { "model": ..., "messages": [...] }
              응답 → choices[0].message.content

  Anthropic:  POST /v1/messages
              { "model": ..., "max_tokens": 1024, "messages": [...] }
              응답 → content[0].text        ⚠️ 구조가 다름

  Google:     또 다름
  로컬(Ollama): 또 다름
```

**옛날에는 이걸 흡수해 주는 게 사실상 LangChain뿐이었습니다.**

### LiteLLM이 하는 일 — 딱 이거 하나

```
┌────────────────────────────────────────────────────────────────┐
│                                                                │
│   [내 코드]                                                     │
│      │  단 한 가지 방식으로만 호출                               │
│      ▼                                                         │
│   [LiteLLM]  ← 얇은 변환기 (100+ 공급사 지원)                   │
│      │                                                         │
│      ├──▶ Anthropic                                            │
│      ├──▶ OpenAI                                               │
│      ├──▶ Google                                               │
│      └──▶ 로컬 모델                                             │
│                                                                │
│   모델 바꾸기 = 문자열 하나 바꾸기                               │
│     "anthropic/claude-..." → "openai/gpt-..." → "ollama/qwen"  │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

**두 가지 사용 형태**:

| 형태 | 설명 | 언제 쓰나 |
|------|------|----------|
| **라이브러리** | 내 파이썬 코드에서 직접 import | 개인 스크립트 |
| **프록시 서버** | 서버로 띄우고 팀 전체가 그 주소만 봄 | 팀 단위 — **비용 집계·키 관리·사용량 제한**을 한 곳에서 |

> 💡 **방송국 관점에서 프록시 형태가 특히 유용합니다.**
> 부서별 사용량과 비용을 한 서버에서 집계할 수 있고, API 키를 개인에게 뿌리지 않아도 됩니다.

### 그래서 "litellm도 이제 된다"의 최종 번역

```
┌────────────────────────────────────────────────────────────────┐
│                                                                │
│  "LangChain을 계속 붙들고 있던 마지막 명분 —                    │
│   즉 '여러 모델을 갈아끼울 수 있다'는 이유마저                   │
│   이제는 더 가볍고 그것만 하는 도구로 해결되니까,                │
│   LangChain을 굳이 쓸 이유가 없어졌다."                         │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

> 💡 **비유**: LangChain이 **만능 공구세트 가방**이라면 LiteLLM은 **멀티 어댑터 플러그** 하나입니다.
> 예전엔 어댑터가 세트 안에만 들어 있어서 세트를 통째로 샀는데, 지금은 어댑터만 따로 팝니다.

### 참고: OpenRouter와의 차이

| | **LiteLLM** | **OpenRouter** |
|---|---|---|
| 정체 | 내가 설치·운영하는 **소프트웨어** | 남이 운영하는 **서비스(중개 API)** |
| API 키 | 각 공급사 키를 내가 다 가짐 | OpenRouter 키 하나만 |
| 데이터 경로 | 내 서버 → 각 공급사 (직결) | 내 서버 → OpenRouter → 공급사 (경유) |
| 비용 | 소프트웨어 무료, 각 공급사에 직접 결제 | 중개 수수료 포함 |
| 보안 | 경유지가 없음 | 한 단계 더 거침 ⚠️ |

> 🔗 배포 교재는 **OpenRouter**를 모델 스펙 비교용으로 소개합니다.
> 실제 서비스 연결에서는 **보안상 LiteLLM(직결)이 더 적합**한 경우가 많습니다.

## 3. ⑤층 — LangChain / LangGraph의 흥망

### LangChain

| 항목 | 내용 |
|------|------|
| **등장** | 2022년 말 |
| **핵심** | "체인(Chain)" — 프롬프트 → 모델 → 파서를 레고처럼 연결 |
| **전성기** | 2023년. LLM 앱을 만들려면 사실상 여기서 시작해야 했음 |
| **왜 식었나** | ① 과한 추상화 ② 디버깅 어려움 ③ **모델이 좋아져서 체인으로 쪼갤 필요가 줄어듦** ④ 각 층에 전문 도구 등장 |
| **현재** | 여전히 널리 쓰이지만, **새로 시작할 때 첫 선택지는 아님** |

> 🎬 "**23년에 만들어진 거라서 사실 되게 옛날 거거든요. 너무 옛날에 만들어진 거죠**"

### LangGraph

| 항목 | 내용 |
|------|------|
| **등장** | 2024년 초 (LangChain 팀의 별도 라이브러리) |
| **왜 나왔나** | 체인은 **한 방향**으로만 흐름 → 루프·분기를 표현 못 함 |
| **핵심** | 노드 + 엣지 + 조건부 엣지 + **State(공유 상태)**, **사이클 지원** |
| **사상** | 스테이트 머신 — 에이전트를 신호등처럼 |

```
LangChain 의 체인            LangGraph 의 그래프
──────────────────           ────────────────────
A → B → C → 끝               A → B ─┬─(통과)→ C → 끝
                                    └─(실패)→ B (되돌아감)
직선 (DAG)                    순환 + 분기 가능
```

**영상의 평가가 정확합니다**:

| 진행자 | 게스트 |
|--------|--------|
| "난 랭그래프 **전도사**인데" | "처음 써보고 **너무 별로**" / "**진입장벽이 높고**" |
| | 하지만: "**단지 랭그래프가 가지고 있는 어떤 사상 같은 게 있죠. 스테이트 머신이라든지…<br>그걸 만드는 건 랭그래프를 따라 하는 게 제일 쉽긴 하죠**" |

> 🎯 **정리**: **라이브러리로서는 호불호가 갈리지만, "상태 + 결정론적 전이"라는 사상은 2026년에 다시 소환되고 있습니다.**
> (→ 6번 문서)

## 4. ③층 — MCP: 도구 연결의 표준

**MCP (Model Context Protocol)** — Anthropic이 2024년 11월 공개한 개방형 규약. 별명은 **"AI계의 USB-C"**.

```
┌────────────────────────────────────────────────────────────────────┐
│  [MCP 이전] — N × M 문제                                            │
│                                                                    │
│    클로드코드 ──전용코드──▶ 깃허브                                  │
│    클로드코드 ──전용코드──▶ 슬랙        3개 앱 × 4개 서비스         │
│    클로드코드 ──전용코드──▶ 노션        = 12개의 연동 코드           │
│    커서      ──전용코드──▶ 깃허브                                   │
│    커서      ──전용코드──▶ 슬랙          ⚠️ 앱이 늘면 곱하기로 늘어남│
│    ...                                                             │
│                                                                    │
├────────────────────────────────────────────────────────────────────┤
│  [MCP 이후] — N + M 문제                                            │
│                                                                    │
│    클로드코드 ─┐                     ┌── 깃허브 MCP 서버            │
│    커서       ─┼── MCP 규약 ─────────┼── 슬랙 MCP 서버             │
│    코덱스     ─┘                     ├── 노션 MCP 서버             │
│                                      └── 사내DB MCP 서버 ← 직접 제작│
│                                                                    │
│    3 + 4 = 7개만 있으면 됨                                          │
└────────────────────────────────────────────────────────────────────┘
```

**하네스와의 관계**:

> 🎬 "우리는 사실 하네스를 만든다고 하면 클로드 코드를 만드는 건 아니고,
> 사실 거기에 들어가는 **툴을 만들거나, MCP를 만들거나, 스킬을 만들거나**"

**즉 MCP 서버를 만드는 것이 실무자가 하는 "하네스 만들기"의 가장 구체적인 형태입니다.**

> 💡 **방송국 활용 예**: 사내 ERP나 편성 DB를 MCP 서버로 감싸면,
> 클로드 코드·커서·코덱스 어느 도구에서든 같은 방식으로 조회할 수 있게 됩니다.
> ⚠️ 다만 **권한 설계를 반드시 먼저** 해야 합니다. (→ 하네스의 안전 계층)

## 5. ④층 — 스킬 / 메모리 / RAG의 관계

셋 다 "필요한 정보를 컨텍스트에 넣는다"인데 **성격이 다릅니다.**

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  RAG          "질문에 답할 지식"을 찾아온다                           │
│               예: "우리 회사 휴가 규정이 뭐야?" → 사규 문서 검색      │
│               → 사실(fact)을 가져옴                                   │
│                                                                      │
│  스킬          "이 일을 하는 방법"을 알려준다                          │
│               예: "월간 보고서 만들어줘" → 보고서 작성 절차서 로드     │
│               → 절차(procedure)를 가져옴                              │
│                                                                      │
│  메모리        "지난번에 있었던 일"을 기억한다                         │
│               예: "저번에 그 스타일로 해줘" → 이전 세션 노트 로드      │
│               → 이력(history)을 가져옴                                │
│                                                                      │
│  ⭐ 셋 다 같은 원리로 동작: 점진적 공개 (필요할 때만 로드)             │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

| | 무엇을 담나 | 누가 쓰나 | 언제 로드되나 |
|---|---|---|---|
| **RAG** | 문서·데이터 | 지식 질의 | 질문할 때마다 검색 |
| **스킬** | 작업 매뉴얼 | 작업 수행 | 해당 작업일 때만 |
| **메모리** | 과거 맥락 | 연속 작업 | 세션 시작 시 / 필요 시 |
| **AGENTS.md** | 프로젝트 규칙 | 항상 | 항상 (그래서 짧게 써야 함) |

> 🎯 **강사용 정리**: "AI한테 우리 자료를 학습시킨다"는 말이 실제로 가리키는 건
> 거의 대부분 **이 네 가지 중 하나**입니다. 파인튜닝이 아닙니다.

## 6. ⑥층 — 하네스 제품들

| 제품 | 성격 | 영상에서의 평가 |
|------|------|---------------|
| **클로드 코드** | 터미널 코딩 에이전트 | "하네스란 무엇인가 → 쉽게는 클로드 코드" |
| **코덱스** | 같은 성격의 경쟁 제품 | Goal, 울트라 기능의 출처 |
| **헤르메스** | 범용/대중형 에이전트 | **fat harness** — "너무 무거워서 다 걷어냈다" |

```
┌────────────────────────────────────────────────────────────────┐
│  하네스의 두께 스펙트럼                                          │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│   얇음 ◀───────────────────────────────────────────▶ 두꺼움    │
│                                                                │
│   맨 API 호출     클로드 코드        fat harness                │
│   (직접 다 짬)    (균형)             (다 해줌)                  │
│                                                                │
│   ✅ 통제력 최대   ✅ 실무 최적       ✅ 초보자 친화             │
│   ❌ 손이 많이 감  ─                 ❌ 무거움, 통제 어려움      │
│                                                                │
│   ⭐ 그리고 모델 체급에 따라 최적 두께가 다르다:                 │
│      · 최상위 모델(클로드/GPT) → 두꺼운 하네스도 소화           │
│      · 작은 오픈 모델(Qwen 등) → 얇게 해야 함                   │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

> 🎬 "Qwen 같은 친구들은 이런 거에 되게 힘들거든요. **너무 하네스가 많아서**"
> "**LLM이 똑똑해야만 잘하는 것 같아요**"

## 7. ⭐ 무엇이 무엇을 대체했는가 — 대체 관계표

```
┌────────────────────────────────────────────────────────────────────────┐
│  2023년의 방식              →   2026년의 방식                          │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│  LangChain 으로 다중 모델    →   LiteLLM (얇은 전용 도구)              │
│  LangChain 의 툴 추상화      →   MCP (업계 표준 규약)                  │
│  LangChain 의 체인          →   그냥 한 번에 시키기 (모델이 좋아짐)     │
│  LangChain 의 에이전트      →   각 SDK 기본 제공 (툴 러너 등)          │
│  LangGraph 의 세밀한 그래프  →   ReAct 에이전트 (2025)                 │
│                             →   다시 큰 단위 그래프 (2026) ← 나선      │
│  프롬프트에 매뉴얼 다 넣기    →   스킬 (점진적 공개)                    │
│  대화 기록 수동 관리         →   오토 컴팩트 / 컨텍스트 편집            │
│  파인튜닝으로 사내지식 주입   →   RAG + 스킬 + 메모리                  │
│  "단계별로 생각해봐" 프롬프트 →   (삭제) 모델이 알아서 함               │
│  JSON 강제용 트릭            →   구조화 출력(structured output) 기능    │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

> 🎯 **패턴이 보입니다.**
> **"프레임워크가 하던 일 → 모델이 하거나(흡수), 표준이 되거나(MCP), 얇은 전용 도구로 쪼개짐(LiteLLM)"**
>
> 이게 하네스 무용론이 말하는 "덜어내는 방향"의 구체적 모습입니다.

## 8. 그래서 지금 새로 시작한다면?

```
┌──────────────────────────────────────────────────────────────────────┐
│  2026년 기준 실용적 출발점                                             │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
```
