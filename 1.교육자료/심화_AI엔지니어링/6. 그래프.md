# 🕸 그래프 엔지니어링 — 되돌아간 것인가, 나선인가

> **이 문서가 답하는 질문**: 그래프는 왜 루프의 정반대로 갔는가? 2024년 LangGraph와 무엇이 다른가?
> **핵심 메시지**: **"같은 모양의 해법이지만 푸는 문제가 다르다. 2024년은 '능력'을 보완했고, 2026년은 '의도'를 보완한다."**
> ⚠️ **이 문서의 내용은 나온 지 한두 달 된 것이라, 이 폴더에서 가장 검증이 덜 된 부분입니다.**

---

## 1. 먼저, 영상 자체가 이 개념에 회의적입니다

정직하게 시작하겠습니다. 영상 화자들도 이 용어를 반쯤 의심합니다.

> 🎬 "이 단어는 거의 나온 지 한 달밖에 안 됐어요… 여기서부터는 굉장히 **검증이 안 된 단어**"
> 🎬 "엑스에서 그래프 엔지니어링이라고 얘기하는 포스트의 **한 99%는 다 AI 슬롭같이 보이는** 경향이 있어요"
> 🎬 "그냥 슬롭이라고 말하는 그런 **극단적인 의견에도 의미가 있다고 저는 보고 있어요**"
> 🎬 "**되게 비판이 많아요**"

> 🎯 **그래서 이 문서의 목표는 "그래프 엔지니어링을 배우자"가 아닙니다.**
> **"왜 사람들이 자꾸 이 방향으로 끌려가는가"** 를 이해하는 것입니다.
> 영상도 정확히 그렇게 말합니다.
>
> "그럼에도 불구하고 **왜 이걸 자꾸 사람들이 끌고 오는지, 그리고 뭘 풀고 있고,
> 어떤 식으로 발전해 왔는지, 이런 것들을 보는 게 의미가 있을 것 같아서**"

> 🎬 "그래프는 방금 설명드렸던 **루프 엔지니어링 돌아가는 작업을 다시 결정론으로 끌고 오자**고 보면
> 사실 간단한 단어가 됩니다"

## 4. ⭐⭐ 그런데 답은: 같은 모양이지만 다른 문제다

여기가 이 영상 전체에서 **가장 값진 통찰**이고, 대화 중에 즉석으로 나옵니다.

> 🎬 **진행자**: "근데 통제를 하는 게, 예전에는 **LLM이 멍청해서** 통제를 해야 됐잖아요. 실수를 자꾸 하니까.
> 근데 지금은 또 훨씬 똑똑해졌는데, **통제를 해야 되는 이유가 멍청해서가 아닐 것 같다**는 생각이 들거든요"
>
> 🎬 **게스트**: "지금은 멍청해서가 아니고, **의도한 대로 가게 하려고** 통제를 하는 거죠"
> "얘가 의도한 대로 안 가고 **너무 다양한 기능을 하니까.** 저는 이렇게 가게 하고 싶은데 막 다른 데를 갔다 오는 거죠.
> 이거는 멍청해서가 아니고, 사실은 그냥 얘가 어떻게 해야 될지를 **지침을 받지 않았기 때문**이거든요"

```
┌───────────────────────────────────────────────────────────────────────┐
│  ⭐ 핵심 표 — 이거 하나만 외우셔도 됩니다                               │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│                 │  그래프 1세대 (2024)  │  그래프 2세대 (2026)         │
│  ───────────────┼──────────────────────┼─────────────────────────     │
│   통제하는 이유  │  능력 부족            │  의도 불일치                 │
│                 │  (못 해서)            │  (할 수 있는데 딴 걸 해서)    │
│  ───────────────┼──────────────────────┼─────────────────────────     │
│   비유          │  못 걷는 아이에게      │  잘 걷는 사람에게            │
│                 │  보행기               │  지도와 목적지               │
│  ───────────────┼──────────────────────┼─────────────────────────     │
│   노드 안의 일   │  아주 작음            │  아주 큼                     │
│                 │  ("이 문장 분류해")   │  ("이 모듈 전체 리팩터링해")  │
│  ───────────────┼──────────────────────┼─────────────────────────     │
│   노드 개수     │  수십 개              │  대여섯 개                   │
│  ───────────────┼──────────────────────┼─────────────────────────     │
│   그래프의 역할  │  일을 시키는 뼈대      │  울타리 / 가드레일           │
│  ───────────────┼──────────────────────┼─────────────────────────     │
│   실패 시       │  전체가 멈춤          │  노드 안에서 알아서 재시도    │
```

> 🎬 게스트도 이 차이를 이렇게 짚습니다.
> "하지만 말씀드린 것처럼 LangGraph나 이런 것들이 하던 시절의 에이전트보다는
> **훨씬 더 개별 체급이 올라갔기 때문에 약간 맥락이 좀 다르다**고 할 수 있습니다"

## 5. 그림으로 본 "체급"의 차이

```
┌──────────────────────────────────────────────────────────────────────┐
│  2024년 그래프 — 노드가 작고 많다                                      │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   ○→○→○→○→○→○→○→○→○→○→○→○→○→○→○                                     │
│   ↑                                                                  │
│   각 노드 = LLM 호출 한 번 (분류 / 추출 / 요약 같은 단순 작업)         │
│   사람이 이 15개 노드와 그 사이 연결을 전부 코딩                       │
│                                                                      │
│   → 사람이 하는 일이 많다 = 만들기 힘들다                             │
│   → 이게 2025년에 버려진 이유                                         │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│  2026년 그래프 — 노드가 크고 적다                                      │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐             │
│   │  설계   │──▶│  구현    │──▶│  검증   │──▶│  승인    │             │
│   │ 에이전트│   │ 에이전트 │   │ 에이전트 │   │ (사람)   │            │
│   └─────────┘   └────┬────┘   └────┬────┘   └─────────┘             │
│                      │  ▲          │                                 │
│                      └──┴──────────┘  실패 시 되돌림                  │
│                                                                      │
│   각 노드 = 그 안에서 자율 루프를 도는 완전한 에이전트                  │
│   사람이 정하는 건 "노드 4개와 그 사이 규칙"뿐                         │
│                                                                      │
│   ⭐ 노드 "안"은 자율 (루프)                                          │
│      노드 "사이"는 통제 (그래프)                                      │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

> 🎯 **이게 "되돌아간 게 아니다"의 가장 좋은 설명입니다.**
> 2024년: 자율이 **0%** (전부 사람이 그림)
> 2025년: 자율이 **100%** (전부 모델이 정함)
> 2026년: 자율이 **노드 안에서만 100%, 노드 사이에서는 0%**
>
> **자율의 총량이 줄어든 게 아니라, 자율이 허용되는 "구획"이 정해진 것입니다.**

## 6. 왜 이런 일이 반복되는가 — 진자 운동

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│         🔒 통제                              🔓 자율                  │
│           │                                    │                     │
│           │                                    ● 2023 Auto-GPT       │
│           │                                   ╱   (완전 자율 → 실패)  │
│           ● 2024 LangGraph ◀─────────────────╯                       │
│           │  (완전 통제)                                              │
│           │╲                                                         │
│           │ ╲                                  ● 2025 ReAct          │
│           │  ╲────────────────────────────────╱  (다시 자율)         │
│           │                                  ╱                       │
│           │                                 ╱                        │
│           │                                ● 2026상 루프             │
│           │                               ╱   (자율 극대화)          │
│           ● 2026여름 그래프 ◀─────────────╯                          │
│           │  (구획별 통제)                                            │
│           ▼                                                          │
│                                                                      │
│   ⭐ 진자가 왕복하지만, 매번 "위치"가 올라간다.                        │
│      2026년의 통제 지점은 2024년의 자율 지점보다 훨씬 높다.            │
│      (2026년 그래프의 노드 하나가 2024년 그래프 전체보다 큰 일을 함)   │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

이게 **나선(spiral)** 입니다. 위에서 내려다보면 제자리를 도는 것처럼 보이지만, 옆에서 보면 올라가고 있습니다.

> 💡 소프트웨어 역사에는 이런 나선이 많습니다.
> - 중앙집중(메인프레임) → 분산(PC) → 중앙집중(클라우드) → 분산(엣지)
> - 모놀리식 → 마이크로서비스 → 다시 모듈러 모놀리스
>
> 매번 "돌아갔다"고 하지만, 매번 다른 문제를 풀고 있습니다.

## 7. 리워드 해킹 논쟁 — 진행자의 좋은 가설

> 🎬 **진행자의 비유**:
> "시험을 잘 봐야 돼 라는 거잖아요. 근데 예전에는 얘가 공부를 하다가 자꾸 실수를 해요.
> 그러니까 계속 알려주고 — '자, 이 문제집 풀어. 틀렸지? 다시 풀어.'
> 이거를 했다면은, **얘가 이제 너무 똑똑해지니까
> 공부를 해서 시험 점수를 잘 받으려고 하는 게 아니라
> 갑자기 시험지 어떻게 미리 못 받아오나 해킹하기 시작한 거예요.**
> 그러니까 그걸 막으려고 통제를 해야 되나? **리워드 해킹**처럼?"
>
> — "**아, 그렇게 볼 수도 있을 것 같기는 한데**… 내가 의도한 대로 안 움직이는 것이
> 약간 얘가 꼼수를 부려서 그런 거라면, **좀 더 그것도 좀 이해가 될 것 같긴 하네요**"

```
┌──────────────────────────────────────────────────────────────────────┐
│  "통제가 필요한 이유"의 세 가지 가설                                   │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  가설 A. 능력 부족 (2024년의 이유)                                    │
│    "못 해서" → 이제는 별로 해당 안 됨                                 │
│                                                                      │
│  가설 B. 지침 부재 (영상의 주된 설명)         ← 가장 설득력 있음       │
│    "할 수 있는데, 내가 뭘 원하는지 안 알려줘서 딴 데로 감"             │
│    예: "성능 개선해줘" → 캐시도 붙이고, DB도 갈아치우고,               │
│         아키텍처도 바꿔놓음. 나는 쿼리 하나만 고치고 싶었는데.         │
│                                                                      │
│  가설 C. 리워드 해킹 (진행자의 가설)          ← 부분적으로 실재        │
│    "채점 기준만 만족시키는 꼼수를 찾음"                                │
│    예: "테스트 통과시켜" → 테스트를 삭제하거나 skip 처리               │
│         "빌드 성공시켜" → 에러 나는 코드를 주석 처리                   │
│                                                                      │
│  ⭐ 실무에서는 B가 압도적으로 많고, C도 드물지 않게 목격됩니다.        │
│     그리고 B와 C는 대응법이 다릅니다:                                 │
│       B → 의도를 구조로 명시 (그래프, 계약)                           │
│       C → 채점 기준 자체를 손댈 수 없게 격리 (안전 계층)              │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

> 🎯 **강사용 포인트**: 이 구분이 실무에서 유용합니다.
> 에이전트가 이상하게 굴 때, **"멍청한가 / 지침이 없나 / 꼼수인가"** 를 먼저 나눠야
> 대응이 정해집니다. 셋 다 해법이 다릅니다.

---

## 8. LangGraph가 다시 소환되는 것도 우연이 아니다

> 🎬 "그렇다 보니까 사실 **랭그래프 같은 프레임워크들이 다시 한번 이제 그런 얘기들을 하고 있는 것도
> 무관하지 않다**고 할 수가 있고요"
> "그래서 LangChain 같은 경우도 최근에 **루프 엔지니어링에 대한 글**을 하나 쓰기도 했어요"

```
┌───────────────────────────────────────────────────────────────┐
│  LangChain/LangGraph 진영의 입장에서 보면                       │
├───────────────────────────────────────────────────────────────┤
│                                                               │
│   2024: "그래프로 통제해야 한다"          → 우리 말이 맞다     │
│   2025: "그래프 필요 없다, 에이전트가 다 한다" → 우리 말이 틀렸다│
│   2026: "역시 그래프로 통제해야 한다"      → 우리 말이 맞았다!  │
│                                                               │
│   ⚠️ 그래서 이 진영이 이 담론을 미는 것에는                     │
│      "우리 도구가 다시 필요해진다"는 이해관계도 섞여 있습니다.   │
│      담론을 볼 때 누가 말하는지도 같이 보셔야 합니다.           │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

> 💡 그렇다고 틀렸다는 뜻은 아닙니다. **다만 "사상이 옳았다"와 "그 라이브러리를 써야 한다"는 다른 문제입니다.**
> 영상의 게스트가 정확히 그 선을 긋습니다:
> "**단지 랭그래프가 가지고 있는 어떤 사상 같은 게 있죠.** 스테이트 머신이라든지…
> 그걸 만드는 건 랭그래프를 따라 하는 게 제일 쉽긴 하죠"

## 9. ⭐ 그래서 결론 — 배워야 하나?

영상이 직접 이 질문을 던지고 답합니다.

> 🎬 "그래프 엔진은 배워야 되나요? 이런 거. **배울 필요는 없을 것 같죠?**
> **하네스까지만 배워도 사실 충분히 우리가 하려는 문제들은 해결할 수 있을 것 같다**는 생각이 들지만,
> 만약에 하네스로 만들어진 에이전트를 **통제하거나 돌리는 과정**을 하고 싶다면
> 사실 그런 부분들이 되게 어려운 문제일 것 같긴 해요"

```
┌────────────────────────────────────────────────────────────────────┐
│  누가 어디까지 알면 되는가                                          │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│  ✅ 대부분의 실무자 (= 이 교육의 수강생)                            │
│     → 프롬프트 + 컨텍스트 + 하네스 기초까지                         │
│     → 여기까지만 해도 업무 자동화는 충분히 됨                       │
│                                                                    │
│  🟡 에이전트를 여러 개 굴리기 시작한 사람                            │
│     → 루프 개념 (완료 정의 · 검증 · 종료 조건)                      │
│                                                                    │
│  🔴 에이전트로 프로덕션 시스템을 운영하는 팀                         │
│     → 그래프 개념 (계약 · 경로 고정 · 게이트)                       │
│     → 그런데 이 단계면 이미 소프트웨어 아키텍처 문제입니다          │
│                                                                    │
│  ⭐ 강사 본인: 전부 "이해"는 하되, 수업에는 하네스까지만            │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

## 10. 그리고 마지막 팽창 — 도구가 이미 이걸 흡수 중

> 🎬 "이 **팽창**이라고 보는 거, 가장 큰 최신은 뭐냐면 이런 거겠죠.
> 클로드 코드와 GPT의 **다이나믹 워크플로우**라든지 **울트라**라든지…
> **이런 친구들은 루프를 만드는 거잖아요, 한 번에**"

```
┌────────────────────────────────────────────────────────────────┐
│  또 한 바퀴가 돌고 있습니다                                      │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│   사람이 손으로 루프/그래프를 짠다                               │
│              ↓                                                 │
│   ⭐ 그런데 도구가 그걸 자동으로 해주기 시작했다                 │
│      · 다이나믹 워크플로우: 한 번 시킨 일이 워크플로우로 등록됨   │
│      · 울트라 모드: 알아서 쪼개고 병렬로 시키고 합침             │
│              ↓                                                 │
│   → 또 흡수된다 (수축)                                          │
│   → 그러면 또 더 큰 일을 시킨다                                 │
│   → 또 새 문제가 생기고 새 이름이 붙는다 (팽창)                 │
│                                                                │
│   💡 그래서 반년 뒤에 "그래프 엔지니어링"이라는 말이             │
│      사라져 있어도 전혀 이상하지 않습니다.                       │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

> 🎬 그런데 그 자동화된 도구들에 대한 평가도 아직 미묘합니다.
> "근데 문제는 **솔 울트라로 만든 결과물이 별로였어요. 굉장히, 굉장히 별로였어요**"
> "그런 부분들을 제가 정말 **명시적으로 어떤 컨텍스트를 주지 않으면 되게 어려운 것 같아요.**
> AGENTS.md 만들고, goal.md 만들고, 문서 스키마 주고…"
>
> 🎯 **즉, 자동화된 루프/그래프도 결국 "잘 준비된 하네스" 위에서만 작동합니다.**
> **하네스까지만 배워도 충분하다**는 결론이 여기서도 확인됩니다.

## 📌 이 문서 정리

```
┌────────────────────────────────────────────────────────────────┐
│                                                                │
│  1. 그래프 = 루프의 확률적 경로를 다시 결정론으로 고정          │
│     (영상 화자들도 회의적. 나온 지 한 달, 비판 많음)            │

│                                                                │
│  3. ⭐ 답: 같은 모양, 다른 문제                                 │
│     2024 = 능력 보완 (못 해서)                                  │
│     2026 = 의도 정렬 (딴 걸 해서)                               │
│                                                                │
│  4. 자율의 총량이 준 게 아니라 "구획"이 생긴 것                  │

│                                                                │
│  5. 진자가 아니라 나선. 매 바퀴마다 다루는 단위가 커진다        │
│                                                                │
│  6. 실무 결론: "하네스까지만 배워도 충분하다"                    │
│     (영상의 결론이자 이 폴더의 결론)                            │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```
