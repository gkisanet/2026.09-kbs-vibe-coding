# 🐴 하네스 (Harness) — 모델 바깥의 모든 것

> **이 문서가 답하는 질문**: 왜 "클로드 코드도 하네스"인가? 하네스 무용론은 맞는 말인가?
> **핵심 메시지**: **"모델은 못 바꾼다. 바꿀 수 있는 건 하네스뿐이다. 다만 하네스는 두꺼워지는 게 아니라 얇아지는 방향으로 간다."**

---

# Part 1. 하네스란 무엇인가

## 1.1 어원 — 원래는 욕이었습니다

> 🎬 "하네스가 원래 **말 안장**이잖아요"
> "원래 **노암 브라운**이… 원래 되게 **안 좋은 의미로 썼었어요, 뉘앙스가.**
> 그러니까 **모델이 멍청하니까 그걸 보조해 주려고 하네스, 보조 도구가 필요하다.**
> 근데 시간이 지나고 나면 모델이 똑똑해질 거니까 **하네스는 결국 다 없어질 거다.**"

```
┌────────────────────────────────────────────────────────────────┐
│  단어의 뉘앙스가 3년 만에 뒤집혔습니다                           │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│   [원래 의미 — 비하]              [현재 의미 — 핵심 기술]        │
│   ──────────────────              ──────────────────────        │
│   "목발"                          "핵심 경쟁력"                 │
│   "모델이 못나서 쓰는 보조기구"     "결과를 좌우하는 설계"        │
│   "곧 사라질 임시방편"             "지금 여기서 승부가 갈리는 곳" │
│                                                                │
│   말하자면:                                                    │
│   "AI 목발 엔지니어링" 이라고 놀리던 말이                       │
│   "AI 목발 엔지니어링학과"가 된 상황 😅                         │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

> 🎬 영상의 논평이 날카롭습니다.
> "처음에 하네스라는 용어를 쓴 사람의 의도와는 **전혀 다르게 받아들여져서 쓰이고 있다**"
> "**하네스가 오히려 진짜로 중요함을 현재 상태에서는 반증하고 있지 않나**"

> 💡 소프트웨어에는 원래 **test harness(테스트 하네스)** 라는 오래된 용어가 있었습니다.
> "테스트 대상 코드를 돌리기 위해 주변에 두르는 실행 껍데기"라는 뜻이죠.
> LLM 하네스도 정확히 같은 구조입니다. **모델을 돌리기 위해 두르는 실행 껍데기.**

## 1.2 정의 — 영상이 내린 가장 좋은 정의

> 🎬 "하네스는 **에이전트가 실수하지 않게 하는 장치를 모두** 다 부른다고 볼 수 있을 것 같습니다.
> **내가 원하는 작업을 똑바로 하게 하기 위한 모든 장치**를 다 하네스라고 부르면 제일 좋은 것 같아요"

```
┌────────────────────────────────────────────────────────────────────┐
│  경계선 하나로 정리                                                 │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│    내가 못 바꾸는 것                     내가 바꾸는 것             │
│    ─────────────────                    ────────────────           │
│                                                                    │
│     ┌──────────────┐                  ┌────────────────────┐       │
│     │              │                  │                    │       │
│     │   모델       │  ◀──────────────▶│    하네스          │       │
│     │   (가중치)    │                  │                    │       │
│     │              │                  │                    │       │
│     └──────────────┘                  └────────────────────┘       │
│                                                                    │
│     · Anthropic/OpenAI가 만듦          · 내가 만듦                  │
│     · 학습 끝나면 고정                  · 언제든 고칠 수 있음        │
│     · 골라 쓸 수만 있음                 · 여기서 차이가 남           │
│                                                                    │

│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

> 🎬 "지금은 거의 **모델이 아니면 하네스다**라는 표현이 약간 적절한 표현인 것 같기도 하고요"

## 1.4 ⭐ ③④⑤가 진짜입니다 — 영상의 실전 사례

### 사례 A. 관측 계층 — "에러가 어디 났는지 못 찾는 문제"

> 🎬 "'야, 네가 했던 것 중에서 **에러 난 게 어딘데, 어디 찾아봐**.'
> 그럼 얘가 '어디지?' 찾는 말이에요, 엄청 이렇게 열심히.
> 근데 그걸 제가 만약에 **미리 로그 계층에 넣어주면 보고 바로 확인할 수가 있겠죠.**
> 이런 것들을 만들어주는 것도 사실 하네스의 영역"

```
┌──────────────────────────────────────────────────────────────┐
│  같은 모델, 같은 질문, 다른 결과                               │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  [하네스 없음]                                                │
│   나: "에러 어디서 났어?"                                      │
│   AI: (파일 30개를 열어보며 헤맴)                              │
│       → 토큰 5만 소모, 5분, 결국 못 찾음                       │
│                                                              │
│  [하네스 있음]                                                │
│   ※ 미리 만들어 둔 것: 에러 발생 시 자동으로                    │
│     logs/errors.log 에 파일명·줄번호·스택 기록                 │
│                                                              │
│   나: "에러 어디서 났어?"                                      │
│   AI: (logs/errors.log 한 번 읽음)                            │
│       → 토큰 500, 10초, 정확히 찾음                            │
│                                                              │
│  ⭐ 모델은 똑같다. "미리 만들어 둔 장치"가 결과를 갈랐다.       │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

> 🎯 **이게 하네스 엔지니어링의 정확한 사례입니다.**
> 프롬프트를 더 잘 쓴 게 아니라 **환경을 미리 정비**한 것입니다.
>
> 💡 사람 조직으로 번역하면: **"신입에게 자료를 찾아오라고 시키기 전에, 자료가 어디 있는지 정리해 두는 것."**

### 사례 B. 문서 계층 — AGENTS.md 계층화

### 사례 D. ⭐ 검증 계층 — 이 폴더 전체의 핵심

> 🎬 "여기서 **제일 중요한 거는 검증**인 것 같아요"

```
┌──────────────────────────────────────────────────────────────────┐
│  왜 검증이 하네스의 심장인가                                       │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   에이전트가 자율적으로 돌려면                                     │
│        ↓                                                         │
│   "이만하면 됐다 / 아직 아니다"를 스스로 판단해야 한다             │
│        ↓                                                         │
│   그런데 AI에게 물어보면?                                          │
│        → "✅ 완료했습니다!" (안 했는데도)                          │
│        ↓                                                         │
│   ⭐ 그래서 AI가 아닌 것이 채점해야 한다                           │
│        · 테스트 통과 여부  → 0 또는 1                             │
│        · 컴파일 성공 여부  → 0 또는 1                             │
│        · 린터 통과 여부   → 0 또는 1                              │
│        ↓                                                         │
│   이게 있어야 비로소 루프가 성립한다                               │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

> 🎬 "사실 이런 하네스나 컨텍스트나 이런 것들의 거의 모든 관심사는 대부분 개발로 지금 보이죠.
> 이건 왜 그러냐면 사실은 **개발이 가장 검증이 쉽기 때문**에 그런 것 같아요"

> 🎯 **이 문장이 방송국 업무 판단의 기준이 됩니다.**
> - 코드 → 테스트가 채점 → 자율 루프 가능 ✅
> - 편성 기획안 → 채점기 없음 → 사람이 매번 봐야 함 ⚠️
> - 자막 오탈자 → 맞춤법 검사기가 채점 가능 → 부분 자율화 가능 ✅
> - 원고의 "톤" → 채점 불가 → 자율화 불가 ❌
>

# Part 2. 하네스 무용론 — 진지하게 다뤄야 할 반론

## 2.1 무용론의 주장

> 🎬 "**대부분은 아마 바꾸는 게 아니라 덜어내는 방향으로 갈 것**이라는 게
> 우리가 얘기하는 **하네스 무용론**에 해당하는 얘기긴 합니다."
> "어떻게 생각하세요?" — "**저도 뭐 동의하는 부분이 있습니다. 충분히.**"

```
┌───────────────────────────────────────────────────────────────────┐
│  무용론의 논리                                                     │
├───────────────────────────────────────────────────────────────────┤
│                                                                   │
│   하네스는 "모델의 부족함"을 메우는 장치다                          │
│              ↓                                                    │
│   모델이 좋아지면 메울 부족함이 줄어든다                            │
│              ↓                                                    │
│   그러면 하네스는 필요 없어진다                                     │
│              ↓                                                    │
│   ⭐ 실제로 관찰되는 현상:                                         │
│      하네스는 더해지는 게 아니라 계속 "덜어내는" 중이다             │
│                                                                   │
│   [실증 사례]                                                      │
│   · 2024년: "단계별로 생각해봐(Chain of Thought)" 를 프롬프트에 씀   │
│     → 지금: 모델이 알아서 추론함. 오히려 쓰면 방해됨                 │
│                                                                   │
│   · 2024년: JSON 강제하려고 별별 트릭을 다 씀                       │
│     → 지금: API에 구조화 출력 기능이 있음. 트릭 전부 삭제           │
│                                                                   │
│   · 2024년: "너는 절대로 반드시 꼭!!!" 강조 폭탄                    │
│     → 지금: 그렇게 쓰면 오히려 과잉 반응함. 평범하게 써야 함        │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘
```

> 💡 이건 실제로 벌어지고 있는 일입니다.
> 모델이 좋아질 때마다 **예전 모델용으로 짜둔 프롬프트가 "부채"로 바뀝니다.**
> 안 지우고 두면 새 모델에서 오히려 성능이 떨어집니다.

## 2.2 유용론의 반론

> 🎬 "지금 엄청 잘 만들어진 하네스, 예를 들면 클로드 코드에다가
> 클로드 자리에 **3년 전에 있었던 모델 GPT-4** 이런 거 갖다 넣으면 **다 망가진다는 거 아니에요?**"
> — "**맞습니다**"

```
┌────────────────────────────────────────────────────────────────┐
│  2×2 로 정리하면                                                │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│                    │  좋은 하네스   │  나쁜 하네스              │
│  ──────────────────┼───────────────┼──────────────            │
│   좋은 모델        │   ✅ 최고      │   😐 그럭저럭             │
│   (2026 클로드)    │               │   (능력 낭비)             │
```

# Part 3. 하네스를 "만든다"는 게 무슨 뜻인가

## 3.1 용어가 헷갈리는 지점 — 영상에서도 짚습니다

> 🎬 "제가 하네스 엔지니어링이라는 용어를 들었을 때
> 저는 **하네스를 만드는 사람에 대한 이야기인 줄 알았어요.**
> **하네스를 쓰는 사람에 대한 이야기였군요**" — "**그렇죠**"

```
┌───────────────────────────────────────────────────────────────────┐
│  "하네스 엔지니어링"의 두 가지 뜻                                   │
├───────────────────────────────────────────────────────────────────┤
│                                                                   │
│  ① 만드는 쪽 (극소수)                                             │
│     클로드 코드 자체를 개발하는 일                                  │
│     → Anthropic 엔지니어들의 일. 우리와 무관.                      │
│                                                                   │
│  ② 쓰는 쪽 (우리)                     ⭐ 영상에서 말하는 건 이쪽    │
│     이미 있는 하네스 위에서                                        │
│     · 툴 / MCP 서버를 만들어 붙이고                                │
│     · 스킬을 쓰고                                                  │
│     · AGENTS.md 를 설계하고                                        │
│     · 검증 절차를 붙이고                                           │

│    "백그라운드 실행을 붙이거나, 칸반을 연결하거나" ← 이건 진짜 개발  │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘
```

> 🎬 "우리는 사실 하네스를 만든다고 하면 **클로드 코드를 만드는 건 아니고**,
> 사실 거기에 들어가는 **툴을 만들거나, MCP를 만들거나, 스킬을 만들거나**"

## 3.2 "엔지니어링"이라는 말이 거슬리는 이유

> 🎬 "아니, 뭔가 **엔지니어링이라고 칭하는 게 저는 되게 헷갈렸어요.**
> 어떻게 하면 어쨌든 클코를 잘 쓰냐, 이걸 다르게 부르는 말인 건데.
> 제가 엔지니어링이라는 용어 자체를 되게 좀 **신성하게** 취급을 좀 하고 있나 봐요"

> 💡 이 불편함은 **프롬프트 엔지니어링 때도 똑같이 있었습니다.**
> "채팅창에 글 잘 쓰는 게 엔지니어링이냐?"
>
> 영상도 이걸 짚습니다: "이때도 **이게 엔지니어링이냐, 이거에 대해서 말이 많았는데**"
>
> 🎯 강사에게 유용한 시각:
> **"엔지니어링"이라는 말이 붙는다는 건, 그 일이 '감각'에서 '재현 가능한 절차'로 옮겨가고 있다는 신호입니다.**
> 그게 실제로 그렇게 됐는지는 별개 문제이고, 그래서 매번 논쟁이 붙습니다.

# Part 4. 곁가지지만 중요한 논쟁 — "코드를 안 본다"

영상의 중간에 긴 대화가 있는데, 하네스 이야기와 직결됩니다.

## 4.1 무슨 이야기였나

> 🎬 "코드를 한 줄 안 본 지 1년 됐습니다" / "VS 코드 삭제하고" / "**풀 리퀘스트 올라오면 쓱 훑어요**"
> "코드 안 보고 **AI의 코드 리뷰만 봐요**"
> "**로직을** 풀 리퀘스트에서 보고, 진짜 필요한 경우에만 코드를 살짝 봅니다"

## 4.2 ⭐ 어셈블리 비유

> 그랬을 때 맨 처음에 나왔을 때 다 '아니, 어셈블리 봐야지, 실제로 그게 어떻게 돌아가는지 알아야지.'
> 이렇게 얘기했을 거 아니에요. 비슷한 이치이지 않을까요?

> 🎬 "**코드를 안 봐도 문제는 안 생기는데, 리뷰를 안 하면**
> 프로젝트가 커지고 복잡해질수록 **컨텍스트 관리하는 데도 안 좋고**,
> 에이전트가 이전보다 못한다 싶으면 **코드가 아마 꼬여있을 것이다**"
