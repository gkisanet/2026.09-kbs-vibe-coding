# 🎓 강사용 전달 설계 — 무엇을 넣고 무엇을 뺄 것인가

> **이 문서가 답하는 질문**: 이 심화 내용 중 **무엇을 수업에 넣어야 하고, 무엇은 강사만 알고 있으면 되는가?**
> **핵심 메시지**: **"신조어는 하나도 넣지 말고, 그 신조어들이 공유하는 원리 세 가지만 넣으세요."**

---

## 1. 결론부터 — 3단 분류

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  🟢 수업에 넣는다 (원리)                                              │
│     · 검증이 병목이다                                                 │
│     · 전부 미리 주지 말고 색인만 줘라 (계층화)                        │
│     · 완료 조건을 먼저 써라                                           │
│     · 코드 리뷰는 다음 AI를 위한 것이다                               │
│     → 용어는 안 쓰고 원리만 전달                                      │
│                                                                      │
│  🟡 질문 받으면 답한다 (용어)                                         │
│     · 하네스 / 컨텍스트 엔지니어링 / MCP / 스킬                       │
│     → 먼저 꺼내지는 않되, 물어보면 한 문장으로                        │
│                                                                      │
│  🔴 수업에 안 넣는다 (최신 담론)                                      │
│     · 루프 엔지니어링 / 그래프 엔지니어링                             │
│     · LangChain vs LiteLLM 논쟁                                       │
│     · 노암 브라운 / 보리스 체르니 어원 이야기                          │
│     → 강사의 배경 지식으로만. 반년 뒤 절반은 사라질 말들.              │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

### 왜 이렇게 나누는가

| 이유 | 설명 |
|------|------|
| **수강생은 프로그래밍 비전공자** | 하네스·루프·그래프는 소프트웨어 아키텍처 개념입니다. 배경 없이 들으면 남는 게 없습니다 |
| **용어는 반년 수명** | 영상 화자들도 "검증 안 된 단어", "99%가 AI 슬롭"이라고 합니다 |
| **원리는 10년 수명** | "검증 가능한 일에만 자동화를 걸어라"는 앞으로도 유효합니다 |
| **이미 교재에 다 있다** | 놀랍게도 배포 교재의 결론들이 이 심화 내용과 **정확히 일치**합니다 (아래 2절) |

## 2. ⭐ 좋은 소식 — 기존 교재가 이미 맞는 말을 하고 있습니다

이 심화 내용을 읽고 나서 배포 교재를 다시 보면, **최신 담론이 기존 교재의 결론을 뒷받침**하고 있음을 알 수 있습니다.

| 심화 개념 (2026 최신) | 이미 배포 교재에 있는 것 |
|---|---|
| "검증이 모든 것의 병목이다" | **참고2_AI_도입_판별표** ③번 문항 (검증 비용) |
| "개발만 잘 되는 건 채점기가 있어서다" | 참고2 판별표 ②③번 (정답의 성격 / 검증 비용) |
| 컨텍스트 엔지니어링 | **3-0. CONTEXT_관리.md** 전체 |
| "도구 결과가 창을 채운다" | 3-0. CONTEXT_관리 3.3절 |
| 하네스 = 모델 바깥의 장치 | **2. AI의_이해** 3.5절 ("ChatGPT = 모델이 아니라 시스템") |
| AGENTS.md 로 규칙 주기 | **참고3_AGENTS_템플릿.md** |
| "업로드 ≠ 학습" | 2. AI의_이해 1.5절 5번 |
| 검증을 더 붙여야 한다 | 1-2. 교육과정 (바이브 코딩의 안전성 논리) |

> 🎯 **즉, 교재를 뜯어고칠 필요가 없습니다.**
> 필요한 건 **네 군데의 소폭 보강**뿐입니다. (→ 4절)

## 4. 배포 교재 보강 제안 — 4곳

> 아래는 **선택 사항**입니다. 지금 교재도 충분히 좋습니다.
> 다만 이 4가지를 넣으면 심화 내용과 완전히 정합해집니다.

| # | 대상 파일 | 보강 내용 | 분량 |
|:-:|----------|----------|:----:|
| 1 | `참고3_AGENTS_템플릿.md` | 말미에 **"프로젝트가 커지면 계층화하라"** 한 절 추가 | 반 페이지 |
| 2 | `참고2_AI_도입_판별표.md` | ③번(검증 비용) 문항에 **"채점기가 있는가"** 로 표현 강화 | 두 문단 |
| 3 | `1-2. 교육과정.md` | 바이브 코딩 안전성 설명에 **"완료 조건 쓰기"** 추가 | 한 절 |
| 4 | `2. AI의_이해.md` 또는 3-0 | **"학습"이라는 말의 두 가지 뜻** 정리 박스 | 한 박스 |

### 4-①의 구체안 (그대로 붙여넣기 가능)

```markdown
## 8. 📈 프로젝트가 커지면 — AGENTS.md 를 "지도"로 바꾸십시오

처음에는 이 템플릿 하나로 충분합니다.
그런데 프로젝트가 커지면 AGENTS.md 가 계속 길어집니다.

> ⚠️ **길다고 AI가 더 잘하지 않습니다.**
> 너무 많은 규칙을 한 번에 주면, AI는 다 읽고 다 흘립니다.
> (사람에게 300페이지 사규집을 통째로 주는 것과 같습니다)

**해법: AGENTS.md 는 짧게 두고, 나머지는 나눠서 "어디를 보라"고만 적으십시오.**

    AGENTS.md  (80줄 이내)
     ├─ 프로젝트 개요
     ├─ 절대 하지 말 것 (짧게)
     └─ 📍 참조 지도
          · 디자인 작업 → docs/DESIGN.md 를 먼저 읽을 것
          · 서버 작업   → docs/SERVER.md 를 먼저 읽을 것
          · 배포 작업   → docs/DEPLOY.md 를 먼저 읽을 것

이렇게 하면 AI가 **그 작업을 할 때만** 해당 문서를 열어봅니다.
필요 없는 규칙이 판단을 흐리지 않습니다.

> 💡 최근 AI 도구들의 "스킬(Skills)" 기능이 정확히 이 원리로 동작합니다.
> **"전부 미리 주지 말고, 어디를 보면 되는지만 알려줘라."**
```

### 4-④의 구체안

```markdown
> ### ⚠️ "AI에게 학습시켰다"는 말의 두 가지 뜻

> 이 표현은 서로 다른 두 가지를 가리킵니다. 섞이면 대화가 산으로 갑니다.
>
> | | ① 모델을 학습시킨다 | ② 시스템이 참고하게 한다 |
> |---|---|---|
> | 정식 명칭 | 파인튜닝(Fine-tuning) | RAG / 메모리 / 스킬 |
> | 모델 파일이 바뀌나 | ✅ 바뀜 | ❌ 안 바뀜 |
> | 비용 | 수백만~수천만 원 | 거의 없음 |
> | 소요 시간 | 수일~수주 | 즉시 |
> | 누가 하나 | 전문 인력 | 우리 |
>
> **우리가 "우리 회사 문서를 넣었다"고 할 때는 100% ②번입니다.**
>
> 💡 다만 ②번도 **시스템의 동작은 실제로 바뀝니다.**
> 같은 질문에 다른 답이 나오니까요. 그래서 업계에서는 이걸
> **"인컨텍스트 러닝(In-Context Learning)"** 이라고 부르며 넓은 의미의 학습으로 보기도 합니다.
>
> ⭐ 정확한 표현은 이것입니다:
> **"모델을 학습시킨 건 아니고, 시스템이 참고할 자료를 붙여준 것이다."**
```

## 5. 예상 질문 & 답변 대본

수강생이 이런 걸 물어볼 수 있습니다. 짧게 답하고 넘어가는 게 좋습니다.

| 질문 | 권장 답변 (1~3문장) |
|------|-------------------|
| **"하네스가 뭔가요?"** | "AI 모델 바깥에 둘러친 프로그램 전체를 말합니다. 클로드 코드가 대표적인 예고요, 같은 모델이라도 이걸 어떻게 만드느냐에 따라 결과가 완전히 달라집니다." |
| **"루프 엔지니어링 배워야 하나요?"** | "지금은 아닙니다. 나온 지 두 달 된 말이고, 업계에서도 검증이 안 됐다고 봅니다. 원리는 하나예요 — **완료 조건을 잘 쓰면 AI가 스스로 반복한다.** 그것만 아시면 됩니다." |
| **"LangChain 배워야 하나요?"** | "우리 목적에는 필요 없습니다. 그건 프로그램 안에 AI를 넣을 때 쓰는 도구인데, 요즘은 그것도 안 쓰는 추세입니다." |
| **"MCP가 뭔가요?"** | "AI 도구에 우리 회사 시스템을 꽂는 표준 규격입니다. USB-C 같은 거라고 보시면 됩니다. 실제로 필요해지면 그때 다루겠습니다." |
| **"코드 안 봐도 되나요?"** | "한 줄씩은 안 봐도 됩니다. 다만 **'무엇을 왜 바꿨는지'는 봐야 합니다.** 안 보면 코드가 꼬이고, 꼬이면 다음번에 AI가 더 못합니다." |
| **"AI가 다 한다는데 우리 일자리는?"** | "지금 확실히 값이 오르는 능력은 **'완료가 무엇인지 정의하는 능력'** 입니다. AI는 '어떻게'는 알아도 '무엇이 좋은 것인지'는 우리에게 물어봅니다." |
| **"우리 회사 문서 학습시킬 수 있나요?"** | "'학습'이 두 가지 뜻입니다. 모델을 바꾸는 건 수천만 원짜리 일이고 우리는 안 합니다. 우리가 하는 건 **AI가 참고할 자료를 붙여주는 것**이고, 이건 오늘 바로 됩니다." |

## 7. ⚠️ 수업에서 반드시 선을 그어야 할 것

이 심화 내용에는 **방송에 그대로 적용하면 위험한 것**들이 섞여 있습니다.

```
┌───────────────────────────────────────────────────────────────────┐
│  ❌ 방송 업무에 적용하면 안 되는 것                                 │
├───────────────────────────────────────────────────────────────────┤
│                                                                   │
│  1. 이벤트 드리븐 + 완전 자율 루프를 방송 콘텐츠에 적용            │
│     예: "특보 뜨면 자동으로 자막 만들어 송출"                       │
│     → 사람 승인 없는 송출은 절대 금지                              │
│     → 자동화는 "초안 생성"까지만. 승인은 반드시 사람.              │
│                                                                   │
│  2. 채점기 없는 일에 루프 걸기                                     │
│     예: "기사 품질이 좋아질 때까지 알아서 반복해"                   │
│     → '좋다'를 채점할 수 없으므로 무한 반복 or 임의 종료           │
│     → 토큰만 태우고 결과는 랜덤                                    │
│                                                                   │
│  3. 되돌릴 수 없는 작업에 자율 실행 권한 주기                       │
│     예: 방송 소재 파일 삭제·이동, 편성표 실제 반영                  │
│     → 반드시 "읽기 전용" 또는 "사본에서만" 으로 시작               │
│                                                                   │
│  4. 사내 자료를 외부 API로 흘리면서 하네스 실험                     │
│     → 심화 개념보다 이게 훨씬 중요합니다                           │
│     → 배포 교재의 로컬/클라우드 판단 기준을 먼저 적용              │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘
```

> 🎯 **한 줄 원칙 (수업에서 강조)**
> **"AI에게 자율을 줄 수 있는 범위 = 틀렸을 때 되돌릴 수 있는 범위"**

## 8. 강사 자신을 위한 실천 3가지

이 심화 내용을 읽고 강사 본인이 **직접 해보면 좋을 것**들입니다. 해보면 수업 설명이 완전히 달라집니다.

```
┌────────────────────────────────────────────────────────────────┐
│                                                                │
│  ① AGENTS.md 를 계층화해 보기                                  │
│     현재 프로젝트의 AGENTS.md 를                                │
│     "짧은 지도 + 나뉜 문서들"로 바꿔 보고 차이를 체감            │
│     → 원리 ②를 실감나게 설명할 수 있게 됨                       │
│                                                                │
│  ② 완료 조건을 적어서 시켜보기                                  │
│     같은 작업을                                                 │
│      (A) "잘 만들어줘"                                          │
│      (B) 완료 조건 3개를 명시                                    │
│     로 각각 시켜보고 결과 비교                                   │
│     → 수업에서 실제 비교 화면을 보여줄 수 있음 (강력함)          │
│                                                                │
│  ③ 본인의 강의 준비 절차를 스킬로 만들어 보기                    │
│     "내가 교재를 만들 때 이런 순서로 한다"를 문서화해서 스킬로    │
│     → 영상의 "논문 억셉" 사례와 같은 구조                        │
│     → 수강생에게 보여줄 수 있는 가장 설득력 있는 사례가 됨        │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

> 💡 특히 ③은 이 영상 전체의 결론과 맞닿아 있습니다.
> **"AI가 여러분의 일을 대신하는 게 아니라, 여러분의 일하는 방식을 매뉴얼로 적어야 AI가 그걸 대신할 수 있습니다."**
> 강사 본인이 이걸 해본 경험담만큼 좋은 수업 자료는 없습니다.
