# 🔁 루프 엔지니어링 — "프롬프팅하지 말고 루프를 만들어라"

> **이 문서가 답하는 질문**: 루프란 정확히 무엇이며, 왜 "프롬프팅을 하지 말라"고까지 말하는가?
> **핵심 메시지**: **"루프 = 종료 조건을 사람에게서 에이전트에게로 넘기는 것. 그러려면 '언제 끝인지'를 기계가 채점할 수 있어야 한다."**

---

## 1. 두 개의 선언

2026년 상반기, 거의 같은 시기에 두 가지 이야기가 이 용어를 밀어 올립니다.

> 🎬 "**절대로 더 이상 코딩 에이전트에 프롬프팅을 하면 안 된다. 너는 루프를 만들어야 된다**"
> — 널리 확산된 글

> 🎬 "거의 같은 날에 이제 **보리스 체르니**가 또 어디 나와가지고 하는 말이,
> **이젠 더 이상 우리는 클로드 코드에다가 프롬프팅을 하지 않는다**"
> — 클로드 코드를 만든 사람 본인

> 💡 두 번째가 무거운 이유: **하네스를 만든 당사자**가 "우리는 프롬프팅을 안 한다"고 말한 것이기 때문입니다.

## 3. ⭐ 루프의 정확한 정의 — 오해 정리

### 오해 ①: "반복하면 루프다"

**아닙니다.** 반복 자체는 옛날부터 있었습니다. (ReAct 에이전트가 이미 반복합니다)

```
ReAct 루프            vs           루프 엔지니어링
────────────                      ────────────────
생각→행동→관찰 반복                  실행→채점→재실행 반복
"다음 행동"을 스스로 정함             "끝났는지"를 스스로 정함
한 턴 안에서 돎                      여러 턴/세션에 걸쳐 돎
종료 = 답이 나오면                   종료 = 성공 조건 충족되면
```

> 🎯 **차이는 "종료 조건을 누가 들고 있는가"입니다.**

### 오해 ②: "휴먼 인 더 루프도 루프 아닌가?"

영상에서 진행자가 정확히 이 질문을 합니다.

> 🎬 "내가 한 루프 끝날 때마다 내가 가서 개입하는 건 루프 아니에요? Human in the loop?"
> — "여기서는 **그건 빼고 얘기하는 것 같아요.**
> 왜냐하면 루프 엔지니어링의 가장 대표적인 사례가 **Goal**이거든요.
> **Goal은 제가 개입하는 게 아니잖아요.**"

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│   Human in the Loop  =  사람이 루프 "안에" 있다               │
│                         (매 회전마다 사람이 판단)             │
│                                                              │
│   Loop Engineering   =  사람이 루프 "밖에" 있다               │
│                         (루프를 설계만 하고 빠진다)           │
│                                                              │
│   ※ 둘은 배타적이지 않습니다.                                 │
│     루프를 돌리되 "이런 조건이면 사람을 불러라"를              │
│     설계에 넣는 게 실무의 정답입니다.                          │
│     (→ 계약의 "에스컬레이션 규칙")                            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 4. Goal — 루프의 대표 사례

> 🎬 "궁극적인 목표를 하나 주고, 골처럼 하나 주고, 그다음에 얘가 알아서 뭘 해보고,
> **그 목표를 자기가 알아서 판단을 해보고, 별로면 다시 되돌아가서** 루프 도는"

### 잘 쓴 Goal vs 못 쓴 Goal

```
❌ 못 쓴 Goal (사실상 그냥 프롬프트)
────────────────────────────────────
목표: "로그인 기능을 잘 만들어줘"

→ 문제: "잘"이 뭔지 에이전트가 모른다.
        스스로 채점할 수 없다 → 루프가 안 돈다.
        결국 한 번 만들고 "완료했습니다" 하고 끝난다.


✅ 잘 쓴 Goal
────────────────────────────────────
목표: 이메일/비밀번호 로그인 기능 구현

완료 조건 (전부 충족해야 함):
  □ tests/auth/ 의 모든 테스트가 통과한다
  □ 비밀번호가 평문으로 저장되는 코드 경로가 없다
  □ 로그인 API 응답이 200ms 이내다
  □ 린터 경고가 0개다

검증 방법:
  · pytest tests/auth/ -v
  · grep -r "password" --include="*.py" 로 평문 저장 확인
  · scripts/bench_login.sh

금지:
  · 기존 users 테이블 스키마 변경 금지
  · 외부 인증 라이브러리 추가 금지

막히면:
  · 스키마 변경이 불가피하다고 판단되면 중단하고 보고할 것
```

> 🎯 **루프 엔지니어링의 실체는 "프롬프트 쓰기"가 아니라 "완료 정의(Definition of Done) 쓰기"입니다.**
> 그리고 이건 **좋은 관리자의 역량과 완전히 같은 것**입니다.

> 🎬 진행자가 정확히 이 결론에 도달합니다.
> "어떻게 돌아야 이게 잘 된 건지 아닌지를 **스스로 판단할 수 있게끔까지 우리가 잘 짜주는 것.**
> 그러니까 **최종 목표를 잘 짜주는 것**이 가장 중요하겠네요"

## 5. 루프의 4가지 종류 (LangChain 정리)

> 🎬 "LangChain 같은 경우도 최근에 **루프 엔지니어링에 대한 글**을 하나 쓰기도 했어요. '아트 오브'라고 해서"

영상이 소개한 4단 구성입니다.

```
┌─────────────────────────────────────────────────────────────────────┐
│  ① 에이전트 루프                                                     │
│     기본형. 도구를 돌리며 일을 한다. (= ReAct)                        │
│     "일단 에이전트를 만들어라"                                        │
│                              ↓                                      │
│  ② 검증 루프 (Verification Loop)                                    │
│     결과물을 채점하고, 부족하면 다시 시킨다                            │
│     테스트 실패 → 고치기 → 다시 테스트 → 반복                         │
│     ⭐ 지금까지 이야기해온 그 루프                                    │
│                              ↓                                      │
│  ③ 이벤트 드리븐 루프 (Event-Driven Loop)                            │
│     사람이 시작시키는 게 아니라, 외부 사건이 시작시킨다                 │
│     "새 문서가 들어오거나, 일정이 트리거되거나, 웹훅이 오거나"          │
│                              ↓                                      │
│  ④ 힐 클라이밍 루프 (Hill Climbing Loop)                             │
│     ①②③에서 문제가 발견되면 → 시스템 자체를 고친다                    │
│     ⭐ 결과물이 아니라 "만드는 방법"을 고치는 루프                     │
└─────────────────────────────────────────────────────────────────────┘
```

### ②와 ④의 차이 — 이게 핵심입니다

```
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│  ② 검증 루프 — "이번 결과물"을 고친다                             │
│                                                                  │
│     [뉴스 요약 작성] → [채점: 별로네] → [다시 작성] → [통과]      │
│                                                                  │
│     ※ 다음번에도 똑같이 처음부터 헤맨다                            │
│                                                                  │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ④ 힐 클라이밍 루프 — "만드는 방법"을 고친다                       │
│                                                                  │
│     [뉴스 요약 작성] → [채점: 별로네]                             │
│                            ↓                                     │
│              ⭐ "왜 별로였지? → 리드 문장이 항상 밋밋하네"          │
│                            ↓                                     │
│              ⭐ skills/news-summary/SKILL.md 를 수정               │
│                 "리드 문장에는 반드시 수치나 고유명사를 넣을 것"     │
│                            ↓                                     │
│     ※ 다음번부터는 그 실수를 안 한다                               │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

> 🎬 "별로면 그거를 또 어딘가에 **피드백을 줘가지고 스킬을 고치거나** 이렇게 하겠죠.
> 말씀드렸던 **개선을 자동화하겠다**고 얘기하는 거죠"

> 🎯 **④가 진짜 야심찬 부분입니다.**
> ②는 "AI가 일을 다시 한다"이고, ④는 **"AI가 자기 매뉴얼을 고쳐 쓴다"** 입니다.
> 그리고 이게 **다이나믹 워크플로우**나 **헤르메스의 "스킬을 저장하자"** 와 같은 이야기입니다.

## 6. ③ 이벤트 드리븐이 왜 갑자기 끼어드나

> 🎬 "이거 갑자기 좀 **다른 얘기 같은데요**" — "그렇죠, 이건 좀 다른 얘기죠"

진행자의 의문이 정당합니다. ①②④는 "일을 잘하는 법"이고, ③은 "언제 시작하는가"라서 축이 다릅니다.

```
┌────────────────────────────────────────────────────────────────┐
│  ③은 "개발 중"이 아니라 "운영 중"의 이야기                       │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  [개발 중 루프]   나 → 에이전트 → 코드 완성 → 끝                 │
│                                                                │
│  [운영 중 루프]   ┌─ 24시간 대기 중 ─┐                          │
│                   │                  │                         │
│                   ▼                  │                         │
│           (외부 사건 발생)            │                         │
│                   ▼                  │                         │
│             에이전트 작동             │                         │
│                   ▼                  │                         │
│               결과 처리 ─────────────┘                          │
│                                                                │
│  · 헤르메스처럼 "게이트웨이를 만들어서 리스닝"하는 구조           │
│  · 크론잡("매일 아침 뉴스 모아오기")도 여기 포함                  │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### 영상의 예시가 아주 좋습니다 — 방송에 그대로 적용 가능

> 🎬 "**일론 머스크가 트윗을 딱 썼다** → 이벤트가 생긴 거고,
> 그걸 보고 무언가 **뉴스를 제작**하다가, 별로면 **그레이더** 해가지고…
> 별로면은 이제 그거를 또 어딘가에 **피드백을 줘가지고 스킬을 고치거나**"

```
방송국 버전으로 옮기면:

  [이벤트]  기상청 특보 발령 (웹훅/API 감지)
      ↓
  [실행]    자막 초안 + 앵커 멘트 초안 생성
      ↓
  [검증]    · 특보 등급이 원문과 일치하는가? (기계 채점 가능 ✅)
            · 지역명이 정확한가?            (기계 채점 가능 ✅)
            · 문장이 자연스러운가?          (기계 채점 불가 ⚠️)
      ↓
  [사람]    데스크 승인 ← ⭐ 여기는 절대 자동화하면 안 되는 지점
      ↓
  [힐클라이밍] 데스크가 고친 부분을 모아서 → 스킬 개선
```

> ⚠️ 그런데 이 예시가 **정확히 방송에서 하면 안 되는 것의 경계**도 보여줍니다.
> "기계가 채점할 수 있는 것"과 "사람이 봐야 하는 것"이 섞여 있고,
> 후자를 자동화하면 **방송사고**가 됩니다. → 8번 문서에서 다시 다룹니다.

## 7. 루프가 성립하기 위한 조건 — ⭐ 실무 체크리스트

루프 엔지니어링을 시도하기 전에 다음 5가지가 갖춰졌는지 확인해야 합니다.

```
┌──────────────────────────────────────────────────────────────────┐
│  루프 성립 조건 5가지                                              │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  □ 1. 성공 조건이 문장으로 적혀 있는가?                            │
│        "잘 만들어줘" ❌  /  "테스트 전부 통과" ✅                  │
│                                                                  │
│  □ 2. 그 조건을 AI가 아닌 것이 채점할 수 있는가?    ⭐ 가장 중요   │
│        AI에게 물으면 "완료했습니다"라고 함                        │
│        → 테스트 / 컴파일 / 린터 / 스키마 검증 / 정규식 매칭        │
│                                                                  │
│  □ 3. 실패해도 되돌릴 수 있는가?                                   │
│        git 커밋 / 백업 / 샌드박스                                 │
│        → 안 되면 루프 돌리면 안 됨. 사고 남.                       │
│                                                                  │
│  □ 4. 종료 조건이 있는가?                                          │
│        "10회 반복해도 안 되면 중단하고 보고"                       │
│        → 없으면 토큰 다 태우고 무한 반복 (2023년의 그 문제)        │
│                                                                  │
│  □ 5. 사람을 부를 조건이 정의되어 있는가?                          │
│        "스키마 변경이 필요하면 중단"                              │
│        "외부 서비스 결제가 발생하면 중단"                          │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

> 🎯 **2번이 안 되면 나머지가 다 의미 없습니다.**
> 그래서 이 모든 논의가 코딩 얘기뿐인 것입니다. 코딩에는 2번이 이미 있으니까요.

## 8. 실증 사례 — 영상에 나온 "논문 억셉" 이야기

> 🎬 "퇴근하고 연구하는데… **아이데이션부터 노벨티, 실험, 논문 작성 모두 다 코덱스로 해서
> ICML 메인 논문 한 편 억셉됐습니다**"
> "사람이 **방향만 관리**해주고, 출근해서 일하는 동안, 자는 동안 **루프 돌면서 개선**하는데"
> "**LLM 위키 두고** 구조로 **연구 일지 쓰도록** 하고 계속 보고"
> "기존에 **박사 했을 때 어떻게 연구했는지 스킬에 녹여서** 스킬을 만들었다고 하십니다"

이 사례를 위 체크리스트로 분해해 보면 **왜 성공했는지**가 보입니다.

| 조건 | 이 사례에서는 |
|------|-------------|
| 성공 조건 | 실험 지표 개선 (수치로 나옴) |
| **채점기** | **실험 코드가 돌아가고 숫자가 나온다** ← ✅ 있음 |
| 되돌리기 | 코드/실험은 되돌리기 쉬움 |
| 종료 조건 | 사람이 아침에 확인 |
| 사람 호출 | **"다른 방향으로 흘러가면 잡아준다"** ← 휴먼 인 더 루프 |
| **추가 요소** | **본인의 연구 방법론을 스킬로 만들어 넣음** ← ⭐ |

> 🎯 **마지막 항목이 결정적입니다.**
> 영상도 여기에 감탄합니다.
>
> "저게 **딱 베스트 케이스**인 것 같아요. 그러니까 내가 원래 연구를 이런 식으로 하는데,
> **이게 매뉴얼이잖아요.** 매뉴얼 같은 거를 잘 만들어서 넣고, 감독을 하면서…"
>
> **즉, 루프가 잘 도는 이유는 AI가 똑똑해서가 아니라
> "그 사람이 이미 갖고 있던 전문성이 매뉴얼로 옮겨졌기 때문"입니다.**

> 💡 **강사용 메시지 (수업에서 써도 좋습니다)**
> "AI가 여러분 일을 대신하는 게 아니라,
> **여러분의 일하는 방식을 매뉴얼로 적어야 AI가 그걸 대신할 수 있습니다.**
> 그리고 그 매뉴얼을 쓸 수 있는 사람은 여러분뿐입니다."

그리고 영상은 이 관계를 **교수-대학원생**에 비유합니다.

> 🎬 "이게 **교수와 대학원생의 관계**라고 생각하면 비슷한 느낌이기도 해요.
> 너가 알아서 일지 쓰면서 연구해라 하다가, 나는 일지 보고, 미팅 왔을 때
> '어떻게 연구하고 있니? 다른 데로 잘못 넘어갈 것 같으면 — 아니야, 이리로 다시 돌아와'"

## 9. 그리고 남은 문제 — 이게 6번 문서로 이어집니다

루프를 돌리다 보면 이런 일이 생깁니다.

```
┌──────────────────────────────────────────────────────────────┐
│  루프의 부작용                                                 │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  · 검증 에이전트를 언제 불러야 하는지 애매하다                  │
│  · 일을 누구에게 시킬지 에이전트가 알아서 정하는데              │
│    그게 내 의도와 다르다                                       │
│  · "원하는 대로 흘러가지 않을 수가 있으니까"                    │
│                                                              │
│  → 그러면 어떻게 하나?                                        │
│  → ⭐ 그 경로를 다시 사람이 못 박자                            │
│  → 그게 그래프 엔지니어링                                      │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```
